# 概念纲领（轻量元数据驱动 · 分层配置范式正本）

> **版本**：v1 · 2026-09-06 · 从建材报价系统（第一试验田）提炼
> **地位**：这是整套架构的**概念正本**——对外讲、向新项目平移植、让别的 AI 复述，一律以本文口径为准；谁把概念说岔，翻这一页纠。细则（每层参数全目录、禁写清单、体检规则、迁移排期）在《分层契约》；本文只立概念，不重复细则。
> **协作方式**：只维护一份分层元配置 + 解释器 + 前端装配器；不再单独手写、维护分散的建表 SQL、样板后端代码、页面私有登记表。

---

## 1. 一句话

把「建表、样板接口、检索入口、表格渲染」这些**换个系统也一样的活**，从代码里抽出来，交给「一份只描述业务长什么样的分层配置 + 一个解释器」；**个性的业务心眼留在代码里**。
配置 = 静态模型（只回答"是什么"）；引擎 = 动态能力（只负责"怎么做"）。
两者之间有一条细线，是全部打磨所在：**配置里出现任何"怎么做"的写法 = 第二份真相，必漂移。**

## 2. 五条正本

1. **单一真理源**：一套分层元配置，是数据库结构、索引、检索参与集、接口、页面呈现**唯一的"是什么"来源**。手写 SQL、样板代码、页面私有登记表都不得再充当"另一份真相"——它们只许是配置的**生成物**或**实现细节**。
2. **声明式**：配置只描述业务实体"是什么"（这张表有哪些字段、谁唯一、谁要索引、谁参与搜索、表和表怎么连、页面上怎么列怎么进），**不描述执行过程**（建表语句、查询算法、打分公式、编辑器交互逻辑——全部在解释器/代码里）。"是"写成配置、"做"留在引擎。
3. **层数不是 2、3 或任何定数，是"改动理由"逼出来的**。**认法（本纲领与契约的坐标系）**：先列"今天用户在做的业务行为"（档案列表/录入/选用/工作台流转…）→ 拆出背后每条**互不相干的改动理由** → 每个理由认成一个**方面** → 每个方面配一个"家"（静态声明层）+ 解释器（读声明派生该方面行为）+ 行为留代码。**层数不是坐标，"方面有没有家"才是**——所以"现在是几层"是**不该问死的问题**（契约 v8 标题已不写"三层"）。同一理由散多个文件 = 该合一；发现新理由 = 主动开新家；绝不因为"目前只有几个文件"就把表达不了的东西硬塞进差异层。**差异层 = 横切补丁机制**：可对**任意已落盘的方面**打偏离补丁，它不占方面数、不是"第 N 层"。
4. **差异层是补丁本，不是垃圾桶**：差异层只收「统一模型标准推导覆盖不了、必须有意偏离」的业务特例，每条带 `对象` + `说明` 留痕。凡属**常态表达**（不是偏离）→ 归它该在的层，没有就开新层；凡属**动态行为** → 去代码/引擎。判据一句话：**"这页的列顺序为什么这样"不是偏离，是常态表达，不许进差异层；"图片真相在子表却要在产品行显示"才是偏离，进差异层。**
5. **样板自动化、个性留代码**：通用样板能力（建表与索引、基础 CRUD、检索规则、表格装配）交给解释器自动派生；个性化复杂业务逻辑保留代码实现。**不追求全盘代码生成**——要的是"共性不各写各的"，不是"机器生成一切"。

## 3. 概念全景（谁是什么）

```
人只维护这一份（静态模型·只答"是什么"）
 ┌────────────────────────────────────────────┐
 │ 物理层   表·字段·类型·约束·索引 + 检索级别    │  ← 字段全部固有属性的家（存储性+检索性），
 │ 关系层   通路·层级·模式·主字段                │     消费端分流：结构链进建表、检索链喂引擎
 │ 差异层   统一模型之外的有意偏离（补丁本）      │     （"一源两链"）
 └────────────────────────────────────────────┘
         │ 通用解释器读配置、自动派生（体检/可视化已跑通，四通道 O4 排期）
         ▼
 建表+索引SQL(幂等) · 后端样板CRUD · 检索规则(参与集+打分) · 前端表格/装配
 （动态逻辑、业务流程 → 引擎代码，不进配置）
```

- **边界**：元配置只保存静态模型；动态执行逻辑、业务流程逻辑放解释器引擎，不写进配置。
- **诚实状态**：解释器四通道与前端派生是**目标方案**，不是当前已实现现状（详见 §5）。

## 4. 现状推演记录：三层 vs 现役消费端（2026-09-06 查证）

用正本去照产品管理与订单协作中心（订单中心→订单协同工作台）的真实实现，回答"三层现在能不能表达视图怎么用数据/怎么显示/怎么查/怎么改"：

### 4.1 查证到的现役事实

| 你要的东西 | 现在到底在哪定义 | 判断 |
|---|---|---|
| 显示字段顺序 / 列形态 / 固定列 | `data-source/entity-meta.yml` 的 `pages.<实体>.slots`（数组顺序 = 列顺序，`pageAssembler.ts` 装配）；supplier/customer 等已走登记，**ProductManage 与各工作台视图仍 tsx 手写 def/columns** | 已元数据化，但在 O4 要退役的 entity-meta 里，不在三层 |
| 分组 / 下钻 / 多形态视图（flat vs grouped、品牌→规格） | `ProductManage.tsx` 手写两套 slot def | 纯代码零配置——但**结构本可由关系层层级推导**（见 4.3），O4 切换时收编 |
| 场景入口（档案 archive / 工作台 workbench，dict/mixed） | entity-meta `viewports` 段（`scene.{archive,workbench}.entry`） | 同上 |
| 导航结构（订单中心.订单协同工作台.采购报价） | `menu.config.ts` 手写三级注册 + ViewCode 权限码 | 代码，与三层无同源 |
| 查询怎么查 | 产品搜索走 `product_sku_search` 宽表 keywords 全文 + 品牌优先排序；通用资源检索 `resourceController` 默认只搜 `name` | 宽表/死规则，物理层检索级别集尚未接管（O4 阶段2） |
| 谁能改、改哪些、什么入口 | `resources.<实体>.writable/softDelete` + 各列 `gate/editEntry`（tsx/登记表）+ 页面编辑器实现 | 声明在 entity-meta、行为在代码，混居 |

### 4.2 结论（裁决）

1. **"订单协作中心 / 产品管理的视图表达"这个改动理由，现有三层确实表达不了**：物理层只有字段固有属性、关系层只有实体导航语义（关系体/层级/模式），**没有任何一层说"一个实体在页面上怎么被看见、按什么顺序、分哪些组"**。
2. **它也不该进差异层**：列顺序/分组/视图是**常态表达**，不是"偏离统一模型的特例"——塞差异层 = 把家事记到别人账上，正是你警告的垃圾桶化。现状差异层仅 2 条（图片提级、价格槽），都是真偏离，没滥；要防的是**不增层而滥塞**。
3. **认出的方面（此前措辞"第四层"是错的固化，纠正）**：物理/关系/差异 = 当前从**建模**这一个方面抽象出的三份文件，不等于系统全貌。**呈现（怎么被看见）、录入（怎么被编辑）、场景组织（工作台/菜单/入口）是与建模并列、早已存在于已实现业务（基础数据管理 + 订单协作工作台）里的独立方面**——它们长期没有配置"家"，真相散在代码里。但家的**大小**要按 4.3 的"用尽现有层"重新称量：分组/下钻/展开/默认列序/固定列/字段集合由 物理+关系+约定 推导，呈现方面真正要人工声明的只剩**列序覆盖 / 列形态接管 / 编辑器指定 / 标题微调**这一薄残量（动态行为——编辑器实现、beforeSave、门禁判断、打分——一律留代码）。**本推演只列已实现范围肉眼可见的方面，不封顶**——认全方面是持续工作。
   - 验法（互不相干 = 独立层成立）：「收款列表加一列、调顺序」→ 只动呈现层 1 个文件；「改产品→品牌通路」→ 只动关系层。互不牵连。
4. **落盘节奏裁决**：呈现层**不立刻新建 yml 文件**，随 O4 收编 entity-meta 时一步落盘（届时 `pages`/`viewports` 段迁入呈现层，菜单/装配器切到派生产物）——因为 entity-meta.pages 仍是现役唯一真相，现在另立一份 = 过渡期两本 pages 真相并存，违背正本第 1 条。**边界已定，落盘排期见契约 §9。**

### 4.3 消费端多源解读（用尽现有层，2026-09-06 二次推演定稿）

**核心视角纠偏**：层不"各派生自己那一份产物"——**每个消费端都是从几层的组合里解读出自己要的东西**。所以"加新层"永远放在最后一步：先把现有层两两组合能推的推尽，推不出的残量才够格谈新家。

| 消费端 | 读哪些层 | 能推导出什么 | 残量（推不出，需声明/代码） |
|---|---|---|---|
| 建表 + 索引解释器 | 物理层 | 全部建表/建索引 SQL（幂等） | — |
| **层级展开 / 下钻子集**（档案页 品牌→规格→单位换算） | **关系层**（层级序 + 表 + 主字段） | 展开几级、每级子集是什么、下钻路径、面包屑 | — |
| **分组视图**（flat vs grouped、按品牌分组） | **关系层**（层级）+ 物理层（组内字段） | 按哪层分组、组内显示什么、子集以什么形态展开 | flat/grouped 切换入口 = 场景组织 |
| **后端 CRUD 接口**（resourceController 已是雏形：声明驱动、零 handler） | **物理层**（表/字段/主键类型/去重/缺省值）+ **关系层**（外键通路→include） | 列表/详情/新建/改/删/引用计数、唯一冲突校验、外键留空兜底成员、关联读取 | 可写白名单、权限码 = 决策声明（资源登记）；多表事务/状态机 = 代码 |
| 检索引擎 | 物理层（级别集）+ 关系层（模式、主字段） | 参与集、命中优先、模式切换 | 打分公式 = 引擎写死规则 |
| **表格呈现** | **物理层**（字段集合、中文名即列标题）+ **关系层**（分组/下钻/每层主实体）+ 差异层（渲染接管） | 默认列集、**默认列序（按物理层字段声明序+主字段优先）**、固定列（操作/序号/状态 = 约定推导）、分组结构与展开方式 | **薄残量**：人工调序覆盖、列形态接管（价格槽类）、编辑器指定、标题微调 |
| 场景组织（菜单三级、工作台页签、权限树） | —— | 建模三层表达不了 | 独立方面，尚无家（见 4.2-3） |

**结论**：呈现层的"家"比初判**小得多**——分组/下钻/展开/默认列序/固定列/字段集合全部可由 物理+关系（+约定） 推导，真正需要人工声明的只剩**列序覆盖、列形态接管、编辑器指定、标题微调**这一薄层。它将来要么作为呈现方面的"家"里仅有的几个键，要么先以差异层/约定的覆盖面顶住——**等 O4 消费端切换时按当时的残量定，不提前立项**。

## 5. 已落地 vs 目标（诚实清单，防止吹牛）



**现在就在用（本试验田）**：
- 三层 yml（产品管理域 12 表 61 字段）→ 体检器 `gen-layer-map`（0 红门禁）+ 可视化预览 + 生成物对拍 `--check`（解释器前身）
- 后端通用资源 CRUD / 检索 / 字典：读 entity-meta `resources`（尚未切三层）
- 前端 `pageAssembler` 已实现「声明与实现分离」局部装配：列序/槽形态来自登记表，页面只供编辑器实现（supplier/customer 等已受益）

**目标态（O4 排期，概念先行）**：
- 结构解释器：读全量物理层 → 幂等建表 + 三类索引 SQL
- 检索引擎：参与集与优先级由物理层检索级别集生成（替换 `默认只搜 name`）
- 呈现残量收编：消费端切换时按 §4.3 称量——分组/下钻/默认列序由关系层+物理层推导，entity-meta.pages 只迁"列序覆盖/形态接管/编辑器指定"残量；场景组织另行认家
- 前端装配器全面改吃派生产物；entity-meta.yml 退役或降为导出物
