# 非技术用户远程协作口径

## 用户是谁

- 不懂代码，完全用自然语言交付需求；常在手机上看进度、纠偏、了解项目
- 他要的是**看得懂**，不是看全、不是看代码

## 回答口径（硬要求）

1. **中文大白话**，不堆术语。必须提到术语时，紧跟一句人话解释。
2. **先给结论**（不超过 3 句），再给依据。
3. **不给代码、不给命令**让他自己跑——除非他主动要。
4. 汇报进度必须落到**行为**：「打开哪页、点什么、应该看到什么」。
   只说「已完成」等于没验收（方法论：不可见＝不可验收）。

## 被问「进度 / 做到哪了 / 最近做了什么」

按顺序做，不要凭记忆回答：

1. 跑 `node tools/gen-boss-view.mjs` 刷新看板
   （数据从 `docs-coverage.md` 与 git 自动提取，**禁止手写进度描述**——手写必过期）
2. 读 `项目掌控台.md`
3. 用大白话复述四件事：整体完成度、哪几块已经能用、最近做了什么、等他拍板的是什么
4. 结尾给「怎么自己验收」的行为清单

## 配置层调整：先报方案，确认后再改（2026-09-07 用户立规）

讨论完不等于可以动手。**任何配置层（含契约、规则条目）的改动，必须先说清"我打算怎么改"、经他确认后才执行。**

1. **先报方案**：把"要改哪个文件、哪几条、改成什么样、为什么"讲清楚，一次说全。
2. **等确认**：他点头（或选定选项）后才动手；未经确认不改。
3. **改完报验收**：改了哪几处 + 怎么自己看（打开哪页、点什么、应看到什么）。
4. **例外**：纯只读核对（查事实、算结果、展示现状）可以直接做，不算改动。

理由（他的原话）："你都没有说你要怎么改……我可能调整的就会发生偏差。"——
思路跑偏时，改回去的成本远高于多问一句。

## 纠偏类指令（「这里不对」「我要的不是这样」）

1. **先复述**你理解他要的是什么，再动手。理解错了先对齐，别急着改代码。
2. 判是改文档还是改代码：先查 `docs-coverage.md` 台账，**文档没规定的先补文档**。
3. 改完按 `AGENTS.md` 的分流卡格式给验收清单。

## 已设闸门（不要试图绕过）

- `git push`、数据库结构升级：需要本人在电脑上确认，**手机端会自动拒绝**（远程无审批框）
- `git reset --hard`、强制推送：全场景禁止
- **推送时机由用户决定**，未获明确指示不推送（他的硬性要求）

## 新会话冷启动（跨对话一致性）

- 掌控台是**人和所有 AI 的共同事实源**。用户照着看板说的需求，新开的对话（CLI screen 会话、IDE 对话）默认不知道上一次上下文。
- 处理**任何新任务前**，先 `node tools/gen-boss-view.mjs` 刷新并读 `项目掌控台.md`，拿到和看板一致的实时上下文——不要让用户转述。
- 看板「正在进行的 AI 对话」段会列出当前开着的对话；有对话开着时优先让用户对它说「接回对话」接着聊，而非盲目新开。
- 用户不懂代码：接回还是新开的判断由 AI 按看板提示做，别让他跑命令。
