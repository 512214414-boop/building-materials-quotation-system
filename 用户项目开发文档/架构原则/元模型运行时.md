# 架构原则·元模型运行时（元模型驱动全栈行为）

> **职责**：定义"元模型即运行时"这一架构主线的唯一权威——所有表业务的行为差异落在登记表上，前后端统一解读，自动处理渲染 / 确认 / 校验 / 检索 / 门禁 / 引用 / 快照 / 权限 / 审计 / 统计。改行为 = 改登记表 = 改数据，不是改代码。
> 上游方法论：L0「表功能元模型」（九视角）→ 文档落地「文档可视化 · 集合体架子」→ 本文（代码落地主线）。
> 现状盘点：2026-09-01。

## 一、愿景与四条原则

**一句话**：一份登记表，前后端统一解读；维度是行为的切片；新增维度 = 全站获得新能力。

1. **行为也是数据**：每个行为问题（这格能不能点、点开怎么确认、谁有权改、是否快照、空值补什么、记不记审计）都是一个"维度"，登记表逐字段声明。业务差异落在登记表上，不落在代码分支里。
2. **一份真相源**：前端渲染、后端校验/保存/引用/权限/审计/统计，从同一份声明解读。出现两套真相源（前端一套后端一套）＝违规。代码里出现"如果表是 X 就这样"的分支 = 该进登记表了。
3. **解读器按维度驱动**：新增维度 = 登记表加一列 + 解读器加一个行为处理。禁止散落改各视图各服务。
4. **先文档后代码**：本文是主线；每补一个维度，先在文档侧「表功能元模型」补齐视角，再动登记表与解读器。

## 二、已证明的样本：权限

权限已经是声明式双端登记：

| 端 | 登记在哪 | 派生什么 |
|---|---|---|
| 后端 | `backend/src/types/index.ts` → `VIEW_PERMISSION_MATRIX`（角色×视图） | 路由守卫 `requireViewPermission` 自动校验 ro/rw |
| 前端 | `apps/staff/menu.config.ts`（navPath + permissionKey） | 权限树、菜单、按钮显隐自动派生 |

**结论**：双端登记表可行、登记表驱动的"行为"可工作。剩下五项（门禁 / 快照 / 审计 / 统计 / 检索层级）照同一思路推广即可——不是创新，是把已验证的模式复制到没做的行为上。

## 三、行为切面清单（现状盘点 2026-09-01）

| 切面 | 行为问题 | 现状落点 | 声明式？ |
|---|---|---|---|
| 渲染 | 这格显示成什么 | 前端 `entityRelations.ts` + `deriveTableColumns` | 半（E 呈现全，G 部分） |
| 确认 | 点开怎么确认、确认才写 | 前端 `confirmStrategy` 三档（direct/dialog/global） | 半 |
| 检索 | 怎么被找到、搜哪层 | 前端 `suggestField`；检索层级（名称/执行标准/渠道）散落 | 半 |
| 门禁 | 前置未满足点开给什么提示 | 交互外壳复用 `PickerInlineCells` / `PickerEditGate`，**门禁原因 ~19 处手写** | **否** |
| 引用 / 建档 | 名字怎么幂等解析、空补什么 | 后端 `registry.ts`：`quickAdd / ensureByName / ensureByParent / resolveRef` + `RegistryDef` | **✅ 是** |
| 关系读写 | 子表怎么挂、视图怎么映射 | 后端 `*Relations.ts`（customer / supplier / warehouse） | 半 |
| 快照 | 单据行存 ID+当时值 | **每个 service 手写 `resolveLineSnapshots`** | **否** |
| 权限 | 谁能看、谁能改 | 双端登记表派生 | **✅ 是** |
| 审计 | 谁做了什么要记 | ~10 个 controller 手动 `req.audit(...)` | **否** |
| 统计 | 报表口径是什么 | `opsReportService` 硬编码聚合/SQL | **否** |

**结论**：10 个切面，2 个全声明式（权限、引用建档），5 个半声明式，3 个全手写（门禁 / 审计 / 统计）+ 快照手写。全站每个表功能动一次，这 7 个半/否的切面各改各的——这就是"改功能要动五处"的来源。

## 四、九视角 × 代码现状（缺口清单）

| 视角 | 前端 entityRelations | 后端 registry / *Relations | 缺口 |
|---|---|---|---|
| A 身份（层 / 父 / 去重键） | `fieldClass` A/B | `uniqueKey` global/parent | 两套命名，未统一 |
| B 语义（说明 / 必填 / 空补） | 无 | `defaults` + `resolveRef` 默认名 | 前端无；后端有 |

## 五、统一真相源设计

目标：一份 `data-source/entity-meta.yml`，生成前后端两份登记表，从根上消除"改一处要动五处"。

```
entity-meta.yml（唯一真相源：实体 × 字段 × 九视角维度）
   ├─→ 生成 frontend/src/shared/config/entityMeta.generated.ts   （渲染/确认/检索/门禁）
   └─→ 生成 backend/src/services/generated/entityMeta.generated.ts      （引用/建档/默认值/快照/校验）
```

设计原则：

1. **生成区与手写区物理隔离**：`*.generated.ts` 禁止手改；业务特有的 override 写在旁边的 `*.override.ts`，生成器不覆盖。
2. **一个实体先做通（最小闭环）再推广**：category 已跑通（阶段 A）；推广到 product / supplier / order 前先对拍。
3. **对拍后切换**：生成的登记表先与现有手写版并存、跑同一批用例比对输出；一致才切流量，禁止直接替换。
4. **快照与审计与统计逐步进**：阶段 C/D 起，快照字段映射、审计 action、统计口径也进同一份源。

## 六、执行引擎设计

解读器 = 读登记表，按维度分派行为（这是"统一解读"缺的那块核心，现在只有 deriveTableColumns、registry 函数、resolveGate 三小块）：

**前端渲染器**（读字段维度）：
```
值来源(valueFrom) → 单元格形态（字典检索/确认层/纯输入/只读/配置面板）
              → 确认策略(confirmStrategy) → 门禁提示(gate→resolveGate) → 场景截断(scenes)
```

**后端处理器**（读字段维度）：
```
引用解析(resolveRef) → 空值补全(defaults) → 快照取值(snapshotFrom) → 校验(required/unique)
                                    → 审计(action) → 统计口径(indicator)
```

## 七、落地路线图

| 阶段 | 做什么 | 价值 | 风险 |
|---|---|---|---|
| **A 统一真相源最小闭环** | 挑 category：`entity-meta.yml` → 生成前端 + 后端登记表，对拍行为一致 | 证明"一份源两处解读"可行 | 中 |
| **B 补门禁维度** | F 门禁（`gate`）进登记表，解读器 `resolveGate` 出提示 | 门禁一处改全局生效 | 中 |
| **C 快照声明** | H 快照字段映射进登记表（`snapshotFrom`），替代 `resolveLineSnapshots` 多版本 | 单据行加字段不用各 service 找一遍 | 中 |
| **D 审计 / 统计声明** | 审计 action 登记 + 指标口径登记 | "记什么 / 算什么"一处定义 | 中 |
| **E 全量推广** | 所有实体迁到生成版，删手写版 | 全站统一真相源，改一处五面自动跟 | 高（最后做） |

**验收判据（每阶段完成时）**：改一个字段只动 `entity-meta.yml` 一处，前端列表、后端校验、宽表同步、文档侧集合体架子四处自动跟；`node tools/check-docs.mjs` 与前后端构建零报错。
