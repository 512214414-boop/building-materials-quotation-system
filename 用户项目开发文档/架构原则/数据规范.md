# 数据规范

> **适用**：设计或修改任何表结构、字段定义、表间关联/解耦判定、物理删除与停用、缺省值补全。建表前先读本文档，再读对应功能文档。
> **定位**：全系统数据域的**知识库条目**。只讲跨功能通用规则与判定方法，不写实现细节（Prisma 语法、具体表名字段名、代码文件由代码/功能文档承载，见[文档编写规范](./文档编写规范.md)）。
> **顶层依据**：项目设计哲学（约束 5 历史单据不可变、原则 2 分层隔离）。
> **与《表格与交互规范》的边界**：本文档管**数据怎么定义**（表、关联、约束、缺省值）；[表格与交互规范](./表格与交互规范.md)管**数据怎么被操作**（显示、录入、编辑、保存提醒交互、面板）。二者通过「缺省值注册表」衔接：本文档定义缺省值，交互规范引用它定义保存提醒行为。**本文档不写任何界面交互行为；交互规范不写任何表结构定义。**

## 表间关联：一切从一条根本问题推导

**每一条表与表的关联，必须先回答：子记录能否脱离父记录独立存在？**

- 子记录能脱离父记录独立存在、而且必须保留（历史单据）→ **解耦**（快照 + ID）
- 子记录离开父记录就没有意义、跟着父的生命周期走（产品的品牌/单位）→ **强关联**（CASCADE）

这个判断来自约束 5：历史单据是法律事实，档案可以改名/删除，但历史永远不能变。

### 解耦三原则（业务表 → 基础档案的引用）

```
├─ ① 快照存储：业务表保留基础数据的完整文字信息（名称/联系人/电话/地址），创建时锁定
│   └─ 后续查看/打印/对账/统计只读快照——档案改了，历史单子还是当时的样子
├─ ② ID 留存：业务表永久保存基础数据全局唯一 ID（大整数 + 索引）
│   └─ 用于聚合统计，不实时关联档案主表
└─ ③ 统计基于 ID：统计只靠业务表内留存的 ID 聚合计算
```

### 强关联三特征（配置子表 → 父档案 或 业务子表 → 业务父表）

```
├─ 生命周期绑定：父删子必删（CASCADE）
├─ 查询天然包含：查父表自然带出子表
└─ 无独立意义：脱离父表无业务价值（如品牌脱离产品无意义）
```

### 表角色分层：层决定关联基调

不按"哪些表"分，按"表扮演的角色"分——任何新表先判定自己属于哪一层：

| 层 | 角色特征 | 关联基调 |
|----|---------|---------|
| 基础数据档案层 | 独立实体，有增删改查入口，可物理删除 | 被业务表引用 → **解耦** |
| 配置子表层 | 依附父档案的配置明细，父删子必删 | 对父档案 → **强关联 CASCADE** |
| 业务交易层 | 记录已发生事件，创建后锁定不变 | 对档案引用 → **解耦**；对业务父表 → **强关联 CASCADE** |
| 定档冻结层 | 阶段性冻结归档，永不修改、完全自包含 | 对档案引用 → **解耦（快照自包含）**；对原始单据 → 仅引用无 CASCADE |
| 系统配置与审计层 | 权限、配置、日志 | 按具体角色判定 |

**判定流程**（设计任何两张表的关联）：① 这张表属于哪一层？② 子记录能否脱离父记录独立存在？③ 解耦 → 留 ID + 索引 + 快照字段、统计按 ID；强关联 → 物理外键 CASCADE、查询自然带出。④ **关联字段一律 NOT NULL**：业务录入暂缺时由后端按系统兜底补全（见「缺省值注册表」）。

### 档案强联动 vs 业务弱解耦（两套标准严格区分）

| | 档案内部（档案 ↔ 档案附属表） | 档案 ↔ 业务单据 |
|---|---|---|
| 关联强度 | **强绑定**，代码强联动同步 | **弱引用**，只依托 ID 查询 |
| 展示 | 档案改名 → 所有引用页面实时展示新名称 | 单据只固定存储档案 ID，**绝不自动同步**名称/品牌/供应商修改 |
| 删除 | 停用优先，不物理删除；停用后下级仍可读 + 停用标识 | 档案物理删除 → 单据保留做账底，展示标注「对应档案已删除，仅留存历史记录」 |
| 统计 | 通过 ID 实时关联 | 只按单据内留存 ID 聚合 |

**核心硬性规则**：无论档案改名、调整信息，过往已生成的业务单据底层数据永久固定，**不后台批量改写单据内任何存储字段**；仅前端展示时动态调取最新档案内容。

### 物理删除与停用策略（适用于所有基础数据档案）

```
├─ 停用：检索默认过滤，可恢复——已存在的业务记录不受影响
├─ 启用：重新进入检索结果——无副作用
└─ 物理删除：彻底删除档案主表数据——业务记录通过快照字段正常展示，仅档案查阅入口失效
```

- 物理删除前提供引用计数查询，前端二次确认弹窗展示影响范围。
- **不存在单据级联删除**：基础档案删掉，单据保留做账底，只做缺失提示。
- 档案已删除时通过单据跳转查看：识别不存在 → 显示友好提示，页面无报错无崩溃。

## 表内字段：录入可以宽松，存储必须规范

### 判定口诀

- 业务上可留白、但存储上必填的字段 → 必须配置**缺省替代值**，由系统写入层统一补全。
- 业务上必须由用户明确的字段（如单据号）→ 保持必填，但不做前端输入框强制；保存时的提醒交互见[表格与交互规范·录入宽松、保存透明](./表格与交互规范.md)。

### 三层职责：谁守底线、谁补缺、谁不设限

所有"业务可空、存储必填"的字段，必须指定一个合法的缺省替代值，由系统在数据写入层统一补全。禁止前端输入框必填校验、禁止各功能各写各的补全逻辑、禁止为了省事把字段改成可空。

| 层 | 职责 | 为什么 |
|----|------|--------|
| 数据库层 | NOT NULL 约束保持不变 | 底线——数据完整性不因业务宽松而放宽 |
| 后端写入层 | 补全缺省替代值（唯一注册表，幂等创建 + 按名称复用） | 用户不填，系统兜底，且兜底必须幂等不重复 |
| 前端层 | 不做输入框必填限制 | 录入渐进式（先录主要后补次要）；保存时按注册表给出确认提醒（交互见[表格与交互规范](./表格与交互规范.md)） |

> 命名注意：此处"三层职责"（数据库/后端/前端）与[表格与交互规范·表格架构分层](./表格与交互规范.md)的"三层架构"（显示/交互/交付）是不同维度的概念，见「术语消歧」。

### 缺省值注册表（唯一权威）

> 后端统一登记所有"业务可空、存储必填"字段的缺省替代值；前端有同名映射（与后端一一对应），禁止各自硬编码。

缺省替代值按字段类型分四类，规则统一：

| 类型 | 缺省替代值 | 补全说明 |
|------|-----------|---------|
| 引用类（供应商、价格类型） | 系统默认记录 | 幂等创建 + 按名称唯一复用已存在记录；业务表存 id + 名称快照 |
| 字符串类（规格、单位、备注） | 通用占位词（「通用」「件」「待完善」） | 建档时未填 → 自动补占位词 |
| ID 类（分类） | 0（未分类） | 建档时未选 → 0 未分类 |
| 数值类必填但无有效值 | 9999 | 占位大值，配合颜色标记一眼识别"未设置" |

**数值占位 9999 规则**：`9999` 用于"业务可空、存储必填"的数值字段；展示时配合警示色让人一眼识别"这是未设置占位，不是真实数值"；业务计算时必须识别占位值——涉及 9999 的字段不得参与正常运算（或按"未设置"处理）。

### 按名称唯一复用 / 合并

引用类缺省值的补全必须同时满足数据库唯一约束与业务录入灵活性：

```
├─ ① 唯一索引是基础：被补全的引用记录按名称建唯一索引——从数据库层面杜绝重复建档
├─ ② 先按名称查：已存在直接复用其 id，不重复建档
├─ ③ 合并更新：复用已存在记录时，仅覆盖本次提供的字段，未提供字段不清空
│   └─ 用户填了什么就更新什么——破坏面仅限命中的那一条记录
└─ ④ 并发兜底：并发同名创建触发唯一约束冲突 → 回查复用
```

> 显式编辑场景（用户明确指定某条记录并改名）撞上已存在名称时，属真实冲突，报错提示，不走系统合并。

### 宽表检索：高频列表不实时联查多表

高频检索列表（如产品列表）**不实时联查多张表**，建一张扁平宽表冗余展示字段：

```
├─ 行粒度 = 列表展示粒度（产品列表 = 每「规格×品牌」一行）
├─ 冗余字段：展示用的名称/价格/图片 + 检索用的关键词拼接串（keywords 程序自动生成，禁止人工编辑）
├─ 同步时机：源表任何变更 → 重建对应宽表行（保存事务提交后重建，无孤儿无陈旧）
└─ 索引：唯一索引锁行粒度 + 全文索引 + 复合索引（状态+时间 / 筛选维度+状态+时间）
```

> 判断依据：列表是否高频且要展示跨表冗余信息？是 → 宽表；低频联查不建宽表，实时联查即可。

### 表设计检查清单（落地自检）

- [ ] 每个外键/关联字段，业务上是否可能留空？→ 配置缺省替代值
- [ ] 每个必填字段，业务上是否有"先记主要、后补次要"场景？→ 配置缺省替代值
- [ ] 缺省替代值是否已登记到注册表？
- [ ] 引用类缺省值是否已建立名称唯一索引？
- [ ] 名称唯一复用是否实现「先按名称查 → 复用 + 按字段合并更新 → 新建」三态语义？
- [ ] 是否实现并发同名创建回查复用兜底？
- [ ] 数值类必填字段，是否用 9999 占位 + 颜色标记？
- [ ] 前端是否未加输入框必填限制？保存时是否按注册表提示"缺什么、补什么、确认或取消"？

## 组合去重与相似判定（复杂多表 + 扁平录入的去重范式）

> 适用：任何"用户输入一段组合文字 → 映射到多表档案"的去重/建档场景（产品建档、单据行关联档案等）。来源：v11.5~v11.7 实战（把完整拼接串当产品名重复建档 → 根治）。

**为什么需要这套范式**：档案是多表复杂结构（如 产品→规格→品牌→单位），而录入端是**扁平的一段文字**。同一档案有无数种近似表述，字段还可能错位（规格值录进产品名）。此时"按字段分别去重"（产品名→产品表、规格→规格表）永远匹配不上 → 误判新增 → 重复建档。

**三层判定（缺一不可）**：

```
├─ ① 组合值精确去重（底层正确性）
│    在宽表上按「去空格(名称) + 去空格(规格)」拼接的组合完整值精确比对，
│    完全一致 = 同一条 → 静默复用（幂等）。组合值一致即覆盖字段错位（「XX25」+空 ≡「XX」+「25」）。
│    空规格补默认值后也要作为第二个候选组合（「XX」+空 ≡「XX」+「通用」）。
├─ ② 匹配度候选（灰度地带人机共判）
│    精确未命中时，对召回的候选算「档案全名相似度」：
│      匹配目标 = 去空格小写的 产品名+规格+品牌 全名（品牌词必须参与匹配）；
│      相似度 = max(语义段覆盖率, 2-gram token 覆盖率, 编辑距离, 完整包含比例)；
│      语义段覆盖率（多段命中才启用，段子序列命中容错：段长≥3 容忍差1字符、段长≤2 必须全中）；
│      ≥ 阈值（60%）→ 返回候选列表（含匹配度），由用户决策「复用该档案 or 仍要新建」；
│      < 阈值 → 视为新品静默新建。
│    理由：近似但不相等时系统无法自判"就是同一条还是不同产品"，必须交用户，不静默臆断。
│    纯编辑距离对「口语乱序 + 长短差异」不友好（输入「ppr伟星绿色25给水管」vs
│    档案「ppr DN25给水管 伟星绿」仅约 0.5），必须用语义段覆盖率为主（v11.9 升级，用户反馈）。
└─ ③ 候选路径零副作用
      展示候选阶段不创建任何档案/单位；用户确认后（复用/强制新建）才产生写入。
```

**硬性规则**：
- 名称、规格必须是**独立字段**，绝不把拼接串整体当名称存储（拼接串 → 再建档 → 叠一层拼接 = 重复档案）
- 匹配度算法与阈值作为**跨功能常量**统一，不各写各的（`search-scoring.archiveMatchScore`，纯函数可单测）
- 建档幂等校验与唯一约束并行：数据库唯一索引兜底 + 应用层组合去重前置拦截
- 用户明确"仍要新建"（forceNew）是唯一绕过候选的合法入口
- **候选召回禁止前缀 LIKE**：口语输入前缀常不在档案名开头（「伟星绿色25给水管」vs 档案开头「ppr」）→ 直接 miss。应复用全局检索召回通道（FULLTEXT ∪ LIKE 合并去重，`mergeLike` 模式）——FULLTEXT ngram 对无空格中文长串是短语匹配（token 连续才命中），口语乱序输入常 0 召回且会掩埋目标档案，LIKE（任意位置包含）才是可靠通道，两者合并保证不漏召回（v11.9 工程经验）

## 规模驱动设计规则（几十万 SKU / 几千万行）

> 适用：任何涉及检索、去重、候选召回、列表、统计的实现。基线见[顶层设计规范·系统规模基线](../顶层设计规范.md#系统规模基线)，来源：约束 6。

**总原则：数据量级决定查询设计，不允许"按几千条假设"写死**。倒推每条查询：

```
├─ 搜索 / 模糊检索 → FULLTEXT ngram 索引召回（LIMIT 可控候选集）→ 应用层打分排序
│   禁止：全表扫 + LIKE '%x%'、全表拉取应用层过滤
├─ 去重 / 相似候选召回 → 先按「前缀 LIKE / 等值」走 B-tree 索引粗筛（几百内）→ 再算组合值/匹配度
│   禁止：函数包裹列（CONCAT/REPLACE(col)）直接当 WHERE 全表扫描、LIMIT 5000 全表拉取算编辑距离
│   执行规则：多字段前缀粗筛禁止写成 `(colA LIKE 'xx%' OR colB LIKE 'xx%')` 单查询——OR 组合依赖
│   index_merge，优化器可能放弃（合并行数超阈值 → 全表扫）；应拆为**两段独立前缀查询**（各走各的
│   单列索引，确定性最优）后应用层按主键合并去重（v15.2 组合去重工程经验沉淀）
├─ 列表 → 索引分页；默认查询复合索引覆盖（状态+时间 / 筛选维度+状态+时间）
│   禁止：全表排序深翻页、LIMIT offset 过大
├─ 统计 / 汇总 → 索引聚合或预聚合字段；不在事务热路径全表计算
└─ 高频列表展示 → 扁平宽表冗余（见「宽表检索」）
```

**检查点**：
- 查询条件里的列是否被函数包裹（CONCAT/REPLACE/SUBSTR…）且无冗余索引列替代 → 全表扫描风险
- "取一批再算"的 SQL 是否先用可索引条件粗筛 → 候选集必须几百内
- LIKE 是否以通配符开头（%x）→ 不走索引，改前缀/全文检索
- 分页是否用 offset 深翻页 → 改游标或缩小范围
- 需要高频按某维度过滤/排序的列是否有对应复合索引

**反模式**：`LIMIT 5000 全表拉取再算相似度`——几十万行时每次建档几百毫秒到秒级，必然卡死（已整改为前缀索引召回 ≤500）。

## 反模式与术语消歧

### 反模式清单（= 违反上述规则的后果）

**表间关联维度**：
1. 物理外键 CASCADE 从基础档案指向业务数据 → 删档案连历史记录一起删掉（违反解耦）
2. 后台批量改写单据内任何存储字段 → 过往单据不再是法律事实（违反快照）
3. 单据级联删除 → 财务历史账目缺失（违反"单据保留做账底"）
4. 解耦关联声明物理外键 → 外键约束锁死档案删除（违反解耦）
5. 前端依赖嵌套对象读取档案 → 档案删除后页面崩溃（违反扁平快照）

**表内字段设计维度**：
6. 前端输入框必填校验 → 打断渐进式录入（违反三层职责）
7. 各功能各写各的补全逻辑 → 兜底值不一致（违反单一注册表）
8. 为省事把字段改成可空 → 破坏数据库关系完整性（违反 NOT NULL 底线）
9. 前端/后端各自硬编码缺省值 → 一处改动另一处忘（违反同一映射）
10. 显式编辑撞名走系统合并 → 用户改名被静默合并（违反真实冲突报错）

**检索 / 去重维度**：
11. 把拼接串整体当名称存储 → 再建档叠一层拼接 = 重复档案（违反独立字段）
12. 分字段分别去重（名称→A 表、规格→B 表） → 字段错位永远匹配不上，误判新增（违反组合值去重）
13. 全表拉取算相似度 / 函数包裹列当 WHERE → 几十万行必卡死（违反规模驱动）

### 术语消歧

| 术语 | 名称 | 所属维度 |
|------|------|---------|
| 本规范「三层职责」 | 数据库层 / 后端写入层 / 前端层 | 字段缺失值的补全职责划分（数据域） |
| [表格与交互规范·表格架构分层](./表格与交互规范.md)「三层架构」 | 显示层 / 交互层 / 交付层 | 表格组件架构分层 |

两套"三层"仅名称近似，含义完全不同，引用时注意区分，不要混用。
