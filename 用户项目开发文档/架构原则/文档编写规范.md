# 文档编写规范

> **职责**：全库文档的元规范——文档体系怎么组织、每份怎么写、冲突怎么裁决。创建或修改任何开发文档之前必读。
> 顶层依据：知识沉淀（按一类活来写）+ 本项目指导思想（业务为什么）+《项目设计哲学》约束 1/2、原则 6。

## 文档体系（唯一层级）

```
知识沉淀（按一类活来写 · 方法 · 产出能指导开发的指导思想 · 可带到任何项目）
  ↓ 用这套写法填写本现场（一类活 + 对象/过程/角色/看数/工具习惯）
系统业务设计指导思想（本项目填满的正文 · 规范源：文档可视化）
  ↓ 推演出要达成的效果与公共能力
项目设计哲学（这个项目的开发约束与权衡）
  ↓
功能文档（功能细则的唯一权威，自包含：表/字段/接口/保存逻辑）
  ↓
顶层设计规范（8 大设计理念）
  ↓
架构原则（跨功能通用规则：表格、数据、档案管理、实体关系面板…）
```

知识沉淀是写法，不是某一行当的目录。下一项目只带走「按一类活来写」，不要带走本项目的开单/配货/进货。方法强制指导思想写满六条线、效果硬到能约束实现、对着行为实地检测。方法见 `文档可视化/` 独立组「知识沉淀」。

## 唯一裁决链

```
用户当前对话中的最新指令（最高，凌驾一切）
  ↓
知识沉淀（怎么写出能指导开发的指导思想）
  ↓
系统业务设计指导思想（本项目这类活、对象、过程、角色、看数、工具习惯要达成什么）
  ↓
项目设计哲学（开发约束与权衡）
  ↓
功能文档（功能内部细节的唯一权威，自包含）
  ↓
顶层设计规范（设计理念）
  ↓
架构原则（跨功能通用规则）
```

- 用户最新指令 > 一切文档；指令下达后立即同步更新相关文档。知识沉淀 / 指导思想 / 档案五段：先改文档可视化，同一轮再改用户文档。两边打架以可视化为准。
- 业务要达成的效果以指导思想为准（规范源：文档可视化）；功能文档是该功能表/接口/保存逻辑的唯一权威。架构级文档写到功能内部细节即为越权，自动失效。
- 架构级文档必须从一类活效果与顶层理念自上而下演绎，不得矛盾。

## 写作规则

- **规则 vs 实现**：规则写文档，实现由代码承载。架构级文档禁止写组件名、函数名、代码片段、CSS/TS 语法、文件路径、像素值、接口签名。
- **每份文档只回答一类问题**：架构原则管跨功能通用规则；功能文档管功能内部完整细节；运维文档管操作执行。
- **引用代替复制**：跨文档内容用「详见《文档名·章节」」，禁止复制粘贴式重复。一个规则一处定义。
- **标题即 ID**：禁止数字编号标题（`## 一、` `### 1.1`），标题简洁语义化，作为锚点。
- **历史由 Git 负责**：全库**不保留变更记录**，正文不写版本沿革；改动直接更新正文现状。
- **功能文档自包含铁律**：功能文档自己定义本功能涉及的所有表结构、字段命名、关联关系、接口契约、保存逻辑；严禁依赖外部文档补全内部细节；与架构级文档冲突时功能文档为准。
- **表结构锚定展开法**（涉及数据模型时必用）：画骨架（表名+字段+类型+约束）→ 填肉（每字段示例值）→ 标关联（外键带 ID 和名称并箭头指向，如 `specId | BigInt FK | 1759(dn25) →spec.id`）。
- **业务语言优先**：写"业务要怎么做"，不写"技术怎么实现"；技术术语首次出现给中文解释。
- 显式标注待确认项：`> ⚠️ 待确认：...`；禁止隐式知识。

## 架构原则怎么写（推导式规则集）

- 开头放「全文结构」树，再放「适用/职责」声明。
- 每条规则挂在它的源头下（为什么存在），用树形符号表达层级，禁止纯平铺"1. 2. 3."。
- 单份原则上不超过 300 行；复杂规则用表格表达。

## 变更管理

- 先改代码，立即同步文档（同一轮完成）；只改代码不改文档或只改文档不改代码均禁止。
- **两个文档体系**：人看、项目对齐，都以 `文档可视化/` 为准（当前进行时）。`用户项目开发文档/` 是旧基线，很多还没搬过来，给人看的组织不在那里；但 AI 会读到它。所以该更新的两边都更新。
- **必须先改可视化**，同一轮再改用户文档对应处。可视化落后 = 人看到的不是最新；用户文档落后 = AI 按旧基线做错。
- **可视化还没写到的**（功能表、接口、保存逻辑等未搬迁部分）：只改用户文档。
- **两边打架**：以文档可视化为准。
- 任何实质改动只更新正文现状与文档清单；不写变更记录（历史由 Git 负责）。
