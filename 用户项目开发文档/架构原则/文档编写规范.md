# 文档编写规范

> **适用**：创建或修改任何开发文档之前必读。本文档定义"文档体系怎么组织、每份文档怎么写"，是所有文档的元规范。
> **定位**：文档不是历史记录，是**可复用的工程知识库**——像封装的 SDK：抽象、通用、精炼、拿来即用。按本文档写的文档，人看得懂、AI 读得快、不膨胀、可复用。
> **顶层依据**：项目设计哲学原则 6（文档是唯一真理源）、原则 1（复用优先）、约束 2（Token 昂贵）。

---

## 文档是知识库，不是流水账

写进文档的每一句话，先过三个判断：

| 这句话属于 | 写进哪里 | 举例 |
|-----------|---------|------|
| **跨功能可复用的规则**（做什么、怎么判断） | 架构原则 | 多记录字段一列一条完整记录 + 下拉展开；操作列固定首列；数字列禁用原生 number 控件 |
| **某个功能内部的完整细节**（表/字段/接口/保存逻辑） | 该功能文档 | 产品的 SKU 矩阵结构；供应商的双层主键；单据状态机 |
| **当前实现的样子**（组件名、代码语法、像素值、文件路径、技术选型对比） | 不写进文档，代码本身是真相 | 某个组件叫 RecordExpandPanel；某列宽 280px；某文件在 src/xx/xx.ts |

**抽象级别三档**（类比写代码）：

- **硬编码级**：具体页面、具体组件、具体数值 → 只存在于代码，不进文档。写进文档只会过期，改一处忘一处，文档与代码脱节。
- **复用逻辑级**：跨场景通用的规则与判定方法 → 架构原则承载。这是文档的主体，像 SDK 的 API。
- **功能细节级**：本功能特有的一切 → 功能文档自包含承载。

**判定口诀**：这条规则删掉"当前实现"后，放到其他项目还能照做吗？
能 → 是知识库，写进文档；不能 → 是流水账，删掉。

## 文档体系（怎么组织）

按"理解成本"从高到低分层，每层只回答一个问题。**从上往下读理解全局，按需跳读找答案。**

```
项目设计哲学     为什么这么设计（约束与权衡）        ← 不常读，先搞懂全局才读
顶层设计规范     8 大设计理念（设计方向）            ← 理解方向时读
架构原则        跨功能通用规则（知识库条目）        ← 写跨功能代码前必读
功能文档        各功能自包含细节（表/字段/接口）     ← 开发某个功能时只读这一份
技术架构        技术选型 / 部署运维                 ← 部署、选型时读
```

**"做什么，读哪份"**：开发新功能 → 先读对应功能文档；设计表格/交互 → 表格与交互规范；建表 → 数据规范；调布局 → 视觉与布局规范；改导航 → 导航与路由规范；做权限 → 权限与职责规范；部署 → 技术架构。具体映射见 [README](../README.md)。

### 唯一裁决链

遇到"哪份文档说了算"的冲突，从上到下命中即止：

```
用户当前对话中的最新指令（最高，凌驾一切）
  ↓
项目设计哲学（问题背景）
  ↓
功能文档（功能内部细节的唯一权威，自包含）
  ↓
顶层设计规范（8 大设计理念）
  ↓
架构原则（跨功能通用规则）
```

关键规则：
- 用户最新指令 > 一切文档；执行后立即同步更新相关文档。
- 功能文档是该功能的唯一最高依据；架构级文档描述到功能内部细节即为越权，自动失效。
- 架构级文档必须从顶层设计规范的理念自上而下演绎推导，不得矛盾。

## 架构原则怎么写（推导式规则集）

架构原则文档是**推导式规则集**，不是并列清单。组织方式的铁律：**从"为什么"出发，让每条规则都挂在它的源头下——读者能从顶层推导出规则，而不是逐条背规则。**

**结构骨架（一条推导链贯穿全文）**：

```
开头：全文结构树（一眼看全貌）
  ↓
起点：客观事实 / 约束 / 矛盾（为什么）→ 推出核心原则
  ↓
每条规则挂在它的源头下，树形展开（├─ └─），括号标"为什么存在"
  ↓
场景类规则用"决策树 / 分支"组织（什么情况 → 怎么做）
  ↓
反模式标注"断掉哪条链"（不是孤立清单）
```

**每条规则的呈现**：
- 规则名 = 一句话说清"做什么"（树节点）
- 内容 1-3 句
- 括号内标**为什么**（这条规则解决什么问题）——读者看到的是"推导"，不是"规定"

**必须**：
- 开头放「全文结构」树，再放「适用」——让人先看全貌，再进细节
- 用树形符号（├─ └─ │）或箭头（→ ↓）表达层级与推导关系，禁止纯平铺的"1. 2. 3."
- 每条规则可独立成条，但要能看出它从哪个源头来
- 用业务语言，技术术语首次出现给中文解释
- 全文控制在可通读的长度（架构原则单份原则上不超过 300 行）

**禁止**：
- 写组件名、函数名、代码片段、CSS/TS 语法、文件路径、像素值——这些是当前实现，代码承载
- 写"设计背景/历史沿革/迁移过程"——背景属于项目设计哲学，历史属于变更记录
- 写具体功能的表结构、字段命名、接口契约——这些属于功能文档
- 重复已在他处定义的规则——引用代替复制

## 功能文档怎么写（自包含）

**职责**：完整、自包含地描述一个功能的所有部分。**功能文档是该功能的唯一最高依据、唯一逻辑轴心、唯一真理标准**。

**必须覆盖的章节**（以 产品管理.md 为范式参考）：

| 章节 | 内容 |
|------|------|
| 设计哲学与方法论 | 本功能的核心设计动机、推导原则 |
| 列表页布局 | 整体页面结构 + 各列逐项交互说明（含下拉/弹出面板的 ASCII 草图与交互规则） |
| 编辑弹窗完整视图 | 弹窗内分区结构、各分区字段、交互规则 |
| 从交互推导数据结构 | 逐表推导过程 + 字段表（字段名、类型、约束、说明） |
| 数据模型规范 | 关联关系图、关键概念定义、设计要点 |
| 数据库表结构（Prisma 规范） | 每张表的字段名、类型、约束、唯一约束、索引、中文 COMMENT |
| 检索宽表设计（若需要） | 宽表字段、默认值规则、keywords 生成规则、同步时机 |
| 接口设计 | 路由、参数、请求体、返回结构、规则说明 |
| 保存逻辑 | 前端校验清单 + 后端事务流程 |
| 设计原则总结 | 本功能的核心原则清单 |
| 变更记录 | 只保留最近 1 条定档说明 |

**自包含铁律**：功能文档自己定义本功能涉及的所有表结构、字段命名、关联关系、接口契约、保存逻辑；严禁依赖外部文档补全内部细节；与架构级文档冲突时功能文档为准。

## 精炼规则（防膨胀）

- **一个规则一处定义**：同一规则只在主文档定义一次，其他文档用相对链接引用，禁止复制粘贴式重复。
- **删除实现即删除内容**：凡是"当前代码的样子"一律不进文档；文档只写"规则是什么、怎么判断"。
- **每个段落只讲一个决策点**：禁止大段背景铺垫。
- **复杂规则用表格表达**，不用长段落。
- **变更记录只留最近 1 条**：实质改动直接更新正文与顶部版本号，不追加历史。
- **功能文档不设硬性行数上限**，但章节必须完整；架构原则单份以 300 行为上限。

## 写作格式

- **全文中文**；代码注释、接口说明、UI 文案用中文；变量名/函数名可英文并附中文注释。
- **标题即 ID**：禁止数字编号（`## 一、` `### 2.1`），标题简洁、避免特殊字符，作为锚点引用。
- **引用规范**：同文件用标题锚点，跨文件用相对路径 + 锚点；禁止 `file:///` 绝对路径、禁止 `见上文` 模糊引用。
- **业务语言优先**：写"业务要怎么做"，不写"技术怎么实现"；技术术语首次出现括号给中文解释。
- **显式标注待确认项**：`> ⚠️ 待确认：...`；禁止隐式知识（"和之前一样"）。

---

## 变更管理

- **先改代码，立即同步文档**：同一轮对话内完成；只改代码不改文档或只改文档不改代码均禁止。
- **变更定档**：任何实质改动只更新正文与顶部版本号（版本号 + 日期），变更记录只保留最近 1 条定档说明。
