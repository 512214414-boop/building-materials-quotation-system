> **职责**：表功能元模型的**项目实例与代码落点**。通用内核不在这里。
> **通用内核（九组视角维度体系）已上移为 L0 方法论**，真相源 `文档可视化/data-source/methodology.yml` → `items[table-meta-model]`（navId `know-meta`），站点见《文档可视化》侧栏「表功能元模型」，执行卡见 `AGENTS.md` GEN 节。**改维度体系只改真相源，跑 `node tools/gen-docs.mjs`**；本文第四节是它在项目语境下的实例化表述，与真相源冲突时以真相源为准。
> 本文独有的、真相源不管的部分：**第六节产品管理范本**（项目实例）与 **第七节代码落点与升级路线**（项目现状）。这两节留在这里，因为 L0 禁止写项目专名。
> 代码落点：`frontend/src/shared/config/entityRelations.ts`（登记表）+ `deriveTableColumns.ts`（推导引擎）。现状与升级路线见本文第七节。

## 一、这是什么

**一份声明 → 五个面自动产出。**

```
       （填一份登记表）
              │
              ▼
      ┌──────────────┐
      │  推导引擎     │  deriveTableColumns / mergeColumns
      └──────────────┘
              │
   ┌──────┬───┴───┬───────┬────────┐
   ▼      ▼       ▼       ▼        ▼
 表格UI  检索   字典快建  确认策略  接口与权限
```

新增一个表功能 = 填一份登记表。填完即享有现有全部能力：**确认层交互、字典边用边建、全局检索、门禁提示、场景截断、列序统一**。不需要写第二套 CRUD。

## 二、为什么这么干（优势）

| # | 优势 | 具体是什么 |
|---|---|---|
| 1 | **零代码扩展** | 新增功能 = 填表。填完自动享有列表/编辑/检索/快建/确认/权限，不是重写一遍 CRUD |
| 2 | **文档即配置** | 登记表既是人读的文档，也是程序读的数据。不存在「文档写了代码没做」的脱节——它们就是同一份东西 |
| 3 | **变更收敛** | 改一处声明，五个面一起变。从根上消灭「改了列表忘了编辑弹窗」这类各改各的事故 |
| 4 | **形态可推导** | 声明了「层 + 值来源 + 关系基数」，界面形态（矩阵/级联/面板/字典检索）自动推导出来，新页面不用重新设计交互 |
| 5 | **AI 可执行** | AI 拿到填满的登记表就知道怎么做，不用猜、不用翻邻近实现去参照——「就近将就」那类事故从源头断掉 |
| 6 | **拒绝第二套** | 禁止视图手写第二套列/第二套确认。要改就改登记表，override 必须登记在案 |

**反面**：不这么干，每个功能各写一套列、一套检索、一套确认、一套快建。代码臃肿、逻辑交叉，改了这里那里又不对。

## 三、维度怎么组织（多视角切分）

**原则：同一个字段，被多个视角各描述一遍。** 每个视角回答一个独立问题，视角之间不重叠、不遗漏。

| 视角 | 回答什么问题 | 对应你原图的行 |
|---|---|---|
| A 身份 | 我是谁、挂在哪一层 | （原图未覆盖，需补） |
| B 语义 | 我是什么、能为空吗 | 特征说明 |
| C 来源 | 我的值从哪来 | 直接引用字典 / 间接引用字典 |
| D 关系 | 我跟谁有关、双向怎么走 | 本实体引用外部关系表 / 外部引用本实体关系表 |
| E 呈现 | 我长什么样、第几列 | 界面显示字段 / 字段显示顺序 |
| F 行为 | 怎么跟我交互 | （原图未覆盖，需补） |
| G 检索 | 怎么找到我 | （原图未覆盖，需补） |
| H 历史 | 档案改了我跟着变吗 | （原图未覆盖，单据场景才需要） |
| I 权限 | 谁能动我 | （原图未覆盖，需补） |

**你原图六行 = 视角 B、C、D、E 的一部分。** 补上 A、F、G、H、I，才是闭合的一套。

## 四、完整维度清单

**分层**：★必填（不填出不了功能）· ☆默认（不填走缺省）· ○场景（特定层才需要）

### A · 身份视角

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `aggregate.id / name` | 集合体标识与名称，如 `product` / 产品档案 | ★ | 全部 |
| `aggregate.type` | 集合体类型：`archive` 档案 / `doc` 单据 / `dict` 字典 / `bind` 绑定 / `derived` 衍生 | ★ | 形态推导 |
| `entity.name / label` | 实体名与中文名 | ★ | 全部 |
| `entity.table` | 物理表名 | ★ | 接口 |
| `entity.primaryKey` | 主键字段 | ★ | 接口 |
| `entity.layer` | 层：`global` 全局字典 / `subject` 档案主体 / `mount` 挂载 / `row` 行级 / `snapshot` 快照 / `annotation` 标注 / `derived` 衍生 | ★ | 形态、可变性 |
| `entity.parent` | 父实体（决定界面嵌套层级） | ☆ | 形态 |
| `field.key / title` | 字段键与表头 | ★ | 表格UI |
| `field.dataIndex` | 数据字段名 | ★ | 表格UI、接口 |
| `field.dataType` | `string / int / decimal / bool / date / image` | ★ | 表格UI、校验 |

### B · 语义视角

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `field.desc` | 业务含义，一句话说清 | ★ | 文档 |
| `field.example` | 示例值 | ☆ | 文档、测试 |
| `field.required` | 是否必填 | ☆（默认否） | 校验 |
| `field.blankFill` | 空值补全规则，如「分类空→按名称 ensure『未分类』」 | ☆ | 保存逻辑 |
| `field.precision` | 小数位（价格 2 位、换算率 4 位） | ☆ | 表格UI、校验 |

### C · 来源视角（值从哪来）

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `field.valueFrom` | `own` 自身字段 / `dict` 直接引用字典 / `dictVia` 间接引用（维度字典）/ `relation` 关系表 / `config` 配置子表 / `derived` 计算 | ★ | 全部 |
| `field.dict` | 直接引用的字典表，如 `brand` / `category` / `unit` | ○（valueFrom=dict） | 检索、快建 |
| `field.dictUnique` | 字典名是否**全局唯一** | ○ | 改名是否全局生效 |
| `field.dictRenameGlobal` | 改名是否全局生效 | ○ | 改全局、并档 |
| `field.dimDict` | 间接引用的维度字典，如 售价→`price_type`、进价→`supplier` | ○（dictVia） | 检索、快建 |
| `field.configTable` | 配置子表 + 复合键，如 `sale_price(spec×unit×priceType)` | ○（config） | 接口、保存 |
| `field.ownerTable` | 值实体落点，如 `spec.specModel` | ★ | 接口、迁移 |

### D · 关系视角（跟谁有关）

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `relation.table` | 关系表，如 `product_category(product_id, category_id)` | ○ | 接口、保存 |
| `relation.direction` | `out` 本实体→外部 / `in` 外部→本实体 | ○ | 形态、级联 |
| `relation.cardinality` | `1:1 / 1:N / N:1 / N:M` | ○ | 形态、级联 |
| `relation.fk` | 外键字段 | ○ | 接口 |
| `relation.onDelete` | `cascade` 随父删 / `restrict` 有引用禁删 / `decouple` 解耦留快照 | ○ | 删除前置检查 |
| `relation.carry` | 关系携带的额外字段：`isPrimary / isBase / isDisplay / sortOrder / conversionRate` | ○ | 形态、互斥校验 |
| `relation.canMerge` | 是否支持并档（改名时并到已有档案） | ☆ | 改全局 |

### E · 呈现视角

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `field.visible` | 是否显示 | ☆（默认显示） | 表格UI |
| `field.order` | 显示顺序（升序，步长 10 便于插队） | ★ | 表格UI |
| `field.renderMode` | `static / text / number / picker / custom` | ★ | 表格UI |
| `field.width / align / fixed` | 列宽预设 / 对齐 / 固定列 | ☆ | 表格UI |
| `field.scenes` | 场景可见性 `archive / workbench / inventory` | ☆（不填=全场景） | 场景截断 |
| `field.group` | 同组列（开单时拼在一起选用），如 `sku` | ○ | 选品插入 |
| `field.slot` | 动态展开槽位，如 `skuPrice`（按 spec 展开多列） | ○ | 表格UI |

### F · 行为视角（怎么交互）

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `field.confirmStrategy` | `direct` 直接建即选 / `dialog` 二次确认 / `global` 改全局+列影响 | ★ | 确认策略 |
| `field.editForm` | 编辑形态：`confirmLayer` 点值→确认层 / `dictSearch` 字典检索 / `plainInput` 纯输入 / `readonly` 只读 | ★ | 确认策略 |
| `field.gate` | 门禁：前置未满足时的提示语，如「请先选规格」 | ○ | 门禁提示 |
| `field.blankPromote` | 空行确认是否晋升为记录行并自动补新空行 | ○（矩阵） | 空行晋升 |
| `field.quickCreate` | 是否支持边用边建（幂等 ensure，有就复用无才建） | ☆ | 字典快建 |
| `field.deleteCheck` | 删除前置检查：引用计数 / 级联范围 | ☆ | 删除确认 |

### G · 检索视角

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `field.searchable` | 是否进全文 `keywords` | ☆ | 检索 |
| `field.searchLayer` | 检索层级：名称层 / 执行标准层 / 渠道层（到哪层搜哪层的字） | ○ | 检索视图 |
| `field.filterable` | 是否可作表头筛选条件 | ☆ | 检索 |
| `field.filterMode` | `lock` 点选档案锁这一条 / `fuzzy` 失焦文字模糊匹配 | ☆ | 检索 |

### H · 历史视角（单据场景）

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `field.snapshotTo` | 快照到单据行的哪个字段 | ○（单据） | 保存、开单 |
| `field.followArchiveChange` | 档案改名是否回改历史行（**恒为否**） | ○ | 快照隔离 |

### I · 权限视角

| 维度 | 填什么 | 级 | 驱动哪个面 |
|---|---|---|---|
| `entity.permissionCode` | 权限码，如 `product:write` | ☆ | 权限 |
| `field.readonlyRoles` | 只读角色 | ☆ | 权限 |

## 五、新增一个表功能的填空 SOP

1. **画关系图**：实体（框）+ 字段（清单）+ 关系（方向+基数+删除行为）+ 场景。图画不出来 = 需求没讲清，先回现场，不许猜着往下走
2. **推集合体**：按图形态归类（档案/单据/字典/绑定/衍生），类型由图形态定，不靠名词
3. **按图分层**：每个实体落到层上（全局/主体/挂载/行级/快照/标注/衍生）
4. **填登记表**：按第四节的 9 组视角，逐字段填。★必填项一个不能空
5. **推导五面**：跑引擎产出列骨架，视图只补专属 render 作为 override
6. **变更回图**：日后加字段/改关系，先改图改登记表，五面自动跟。禁止绕过登记表直接改某处代码

**自检**：有没有第二套手写列？有没有第二套确认？维度填全了吗（尤其 valueFrom 与 relation 方向）？

## 七、代码落点 · 现状与升级路线

**已有（v22 现状）**：

| 能力 | 落点 |
|---|---|
| 登记表 | `frontend/src/shared/config/entityRelations.ts` — `EntityFieldSpec` / `EntityRelation` |
| 推导引擎 | `deriveTableColumns.ts`（按场景过滤+按 order 排序→列骨架）、`mergeColumns`（合并视图 override） |
| 五面 | 表格UI / 检索（A类 dictSearch）/ 字典快建（dictKind）/ 确认策略（三档）/ 场景截断（scenes） |
| 已迁移视图 | 采购报价（workbench）、产品档案（archive，含 `skuPrice` slot）、库存主表（inventory） |

**现有 `EntityFieldSpec` 已覆盖的维度**：key / title / dataIndex / renderMode / width / align / fieldClass（A·B）/ dictKind / suggestField / confirmStrategy / scenes / order / fixed / slot / pickerGroup

——即视角 **E 呈现**（全）、**F 行为**（确认策略一档）、**C 来源**（dict 一层）。

**缺失、需升级的维度**（本文第四节的其余部分）：

| 缺口 | 要加什么 | 优先级 |
|---|---|---|
| 无 A 层与父实体 | `entity.layer` / `entity.parent` / `entity.table` | 高（形态推导的前提） |
| 无 D 关系完整描述 | `relation` 扩到 direction / cardinality / onDelete / carry / canMerge | 高（级联与删除检查靠它） |
| 无 C 间接引用字典 | `field.dimDict`（售价→price_type、进价→supplier） | 高 |
| 无 C 值来源分类 | `field.valueFrom` 六值枚举 + `ownerTable` | 高（决定单元格形态） |
| 无 F 门禁 | `field.gate` 提示语 | 中（门禁用提示不用静默） |
| 无 F 空行晋升 | `field.blankPromote` | 中（矩阵场景） |
| 无 G 检索层级 | `field.searchLayer` / `filterMode` | 中 |
| 无 H 快照 | `field.snapshotTo` | 中（单据域） |
| 无 B 空值补全 | `field.blankFill` | 低 |

**升级方式**：先扩 `EntityFieldSpec` 类型与 `entityRelations.ts` 的产品登记项，让产品管理成为第一个九视角填满的范本；跑通后再逐个迁移其他实体。禁止在视图里手写这些维度——那等于绕过登记表。
