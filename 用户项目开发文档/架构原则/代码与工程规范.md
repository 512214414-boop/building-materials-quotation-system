# 代码与工程规范

> **适用**：写 / 改前端源码、模块引用、构建校验之前必读。后端 TypeScript 工程同样遵守其中「唯一权威」原则。
> **定位**：源码组织与变更纪律的跨功能通用规则（工程域知识库条目）。
> **顶层依据**：项目设计哲学原则 1（复用优先）、原则 6（文档是唯一真理源 → 源码也必须存在唯一权威）、约束 2（Token 昂贵 → 不养双份）。
> **配套**：可复用的共享组件/函数/配置清单见《共享组件与公共能力》（复用前先查，禁止重复造轮子）。

## 起点：一个客观事实（模块解析契约）

前端工程（Vite + TypeScript）的模块引用有一个固定的解析契约：

- 代码里写 `import 'xx.js'`，存在真实 `xx.js` 文件 → **必然加载它**；
- 不存在 → **自动回退**解析同名 `xx.ts` / `xx.tsx`。

**推论**：只要同目录存在同名 .js，它就永远遮蔽 .ts 权威源码——类型检查看 .ts、运行时跑 .js，两边各说各话（这就是「改了代码页面却没变化」的根因）。本约定是解析器的既定行为，不可配置规避，只能靠「不让 .js 存在」来保证。

---

## 铁律 1：源码唯一权威

- ├─ src 下**只允许 .ts / .tsx 源码，禁止任何 .js 文件**（含同名副本、复制件、历史残留）。
  （为什么：.js 存在即遮蔽 .ts，类型与运行脱节 → 改 .ts 不生效）
- ├─ 全站模块引用统一写 `.js` 后缀（目标为 .ts/.tsx 时由解析器回退）；禁止写 .ts/.tsx 后缀、禁止无后缀与带后缀混写。
  （为什么：一种引用风格 = 解析行为唯一可预期；回退解析正是本约定的设计前提）
- └─ 工程配置文件（构建配置等）同理：同名 .js/.ts 只允许一种，以 .ts 为准。
  （为什么：配置层同样受遮蔽契约约束，双份一样会造成「改了不生效」）

## 铁律 2：变更纪律（防双份再出现）

- ├─ 改代码时**见到同名 .js 必须先删除**，再改 .ts 权威源码。
  （为什么：留着 .js 只改 .ts = 白改；删除是「让修改生效」的前置动作）
- ├─ 新建模块一律 .ts/.tsx，禁止创建 .js。
  （为什么：新代码是唯一权威的起点，不引入第二份）
- └─ 文件类型迁移（如 .js → .ts）必须「重命名式」：旧文件消失、新文件接管；严禁「复制式」新旧并存。
  （为什么：复制式迁移是历史上双份并存的直接成因）

## 铁律 3：构建校验（让双份第一次出现就暴露）

- ├─ 前端构建校验（build:check）内置「源码唯一权威」扫描：src 下发现 .js 即失败，构建中止。
  （为什么：双份不报错 = 潜伏多年无人知；一报错 = 第一分钟就暴露）
- └─ 凡涉及前端工程的整改 / 提交，以构建校验全绿为验收底线。
  （为什么：验收标准即防再犯闸门，与文档验收同一地位）

---

## 反模式（断掉哪条链）

- ┌─ 复制式迁移（旧文件不删）：断「源码唯一权威」→ 双份并存
- ├─ 只改 .ts 不删 .js：断「变更纪律」→ 修改不生效
- ├─ 裸构建不校验：断「构建校验」→ 双份潜伏
- └─ 变更记录先写、代码后改：断「文档与代码同步」→ 文档说已删、实际还在（PATCH 病根）
