# 项目设计哲学

> **版本**：v2.3（2026-08-10）
> **文档定位**：全系统最顶层文档。本文档不讲"要做什么"，只讲"我们面临什么样的客观约束，每个决策要解决什么问题，权衡逻辑是什么"。所有规范、架构、代码决策，必须能在本文档找到对应的问题背景。**理解"为什么"比记住"怎么做"更重要**。
> **文档关系**：本文档 → [顶层设计规范.md](./顶层设计规范.md) → 各架构原则文档 → 功能文档。当规范与问题背景冲突时，以问题背景为准——规范是解决问题的手段，不是目的。

---

## 第一部分：根本性约束（我们无法改变的客观现实）

所有设计决策都必须在这些约束下做权衡。这些约束不因技术选型改变而改变，是本项目的"物理定律"。

### 约束 1：开发者不懂代码，永远不会主动改代码

**客观事实**：
- 项目决策者是建材门店老板，不懂代码、不懂英文、不懂技术术语
- 所有开发、调整、修复，100% 靠中文自然语言与 AI 对话完成
- 用户永远不会打开代码编辑器手动调整，永远不会用 git 回滚
- 出了问题只能靠自然语言描述现象，靠 AI 定位和修复

**直接推论**：系统必须皮实（改一处不崩全局）、一致（相同交互处处一样）、规则显式化（写在文档里，AI 能读到）。**详见原则 1、2、5、6。**

---

### 约束 2：Token 极其昂贵，重复生成 = 浪费 + 不一致

**客观事实**：
- 大模型对话按 Token 计费，上下文越长越贵
- 同样的需求说两遍，AI 生成的结果大概率不一样
- 花十轮调好的组件，重新写一遍又要花十轮重新调
- 项目越来越大，上下文窗口有限，塞不下所有代码

**直接推论**：能复用绝不重复实现，同样的规则只写一次，文档是唯一真理源。**详见原则 1、5、6。**

---

### 约束 3：部署在门店笔记本上，算力 / 网络都有限

**客观事实**：
- 服务器就是前台一台普通笔记本，没有专业运维
- 同时在线：老板 + 2-3 个店员 + 几个客户扫码，最多不超过 10 人
- 网络是店里的普通宽带，可能不稳定
- 笔记本还要干别的（看监控、打微信、开 Excel），不能占满资源

**直接推论**：算力往前放（前端计算），后端只做必要的事（存数据、最终校验），不做高并发架构。**详见原则 3、约束 5 的权衡。**

---

### 约束 4：用户是 Excel 资深用户，操作习惯已经刻在骨子里

**客观事实**：
- 用户用了十几年 Excel 开单，所有肌肉记忆都是 Excel 的
- Excel 的特点：点格子直接敲、回车下移、改数立刻出结果、没有"保存"按钮、不弹打断人的窗
- 店员开单时客户在旁边等着，客户边说店员边敲，是流式录入，不是"填表单"
- 手机端也是店员在用（配送、仓管），不是给小白客户玩的——操作效率优先

**直接推论**：表格是终极交互载体，点格子直接输入，改了立刻生效，输入流不被打断，双端一套界面。**详见原则 3、4。**

---

### 约束 5：历史单据是法律事实，改了就要出大问题

**客观事实**：
- 建材门店的单据是对账、结账、售后的依据，开出去就不能变
- 客户档案、产品档案、供应商档案可能会改名、删除、停用，但历史单子必须永远是当时的样子
- 对账时必须能说清楚"上个月给你送的这批货，当时是这个价、这个牌子"

**直接推论**：业务数据快照存储（开单时抄下当时的名称和价格），基础数据可删但历史不受影响，禁止物理外键 CASCADE 从基础档案到业务数据。**详见原则 2。**

---

### 约束 6：数据量级巨大——几十万 SKU，几千万业务行

**客观事实**（2026-08-10 用户明确，必须作为一切性能设计的输入基线）：
- 使用人数极少：全系统用户只有**几十个**（老板 + 几个店员 + 配送 + 少量客户扫码），**并发极低，绝不考虑高并发**
- 但**数据量极大**：建材门店要卖所有品类（管材管件/电线电缆/开关插座/五金工具/洁具卫浴…），全品类 SKU 高达**几十万条**——仅伟星、日丰两个品牌的一个系列录完就是几百条
- 业务数据（单据、行明细、价格矩阵、配货、成本、收款、操作日志）随经营累积，按**几千万行**规模设计
- 以上数字是**当下明确的规模目标**，不是"未来可能"，任何"按几千条设计"的实现都不合格

**直接推论**（性能设计的唯一输入，逐条倒推验证）：
- **索引驱动一切检索**：搜索/去重/候选召回必须走索引（FULLTEXT、B-tree、复合索引），**禁止函数包裹列导致的全表扫描、禁止全表拉取到应用层再算**（如建档相似候选若全表拉 50 万行算编辑距离必然卡死）
- **宽表 + 冗余列**：高频列表/去重用扁平宽表承载（keywords 全文索引、组合去重列），不实时联查多表
- **候选集受控**：任何"取一批候选再算"的逻辑，候选集必须先用索引粗筛压到可控规模（几百内），再应用层精细打分
- **分页/列表**：列表一律索引分页，禁止全表排序深翻页；单表行数增长不改变响应体验
- **后台聚合**：统计/汇总走聚合索引或预聚合，不在事务热路径全表计算
- **笔记本算力兜底**：上述全部在"普通笔记本 + 单库实例"上成立（约束 3），不允许引入分布式/大数据组件——靠索引与查询设计解决问题

**详见**：[顶层设计规范·系统规模基线](./顶层设计规范.md#系统规模基线)、[数据规范·规模驱动设计](./架构原则/数据规范.md#规模驱动设计规则)。

## 第二部分：从约束推导出的核心设计原则

每个原则按统一模板组织：**解决什么问题 → 原则内容 → 判断标准 → 破例条件 → 反面教材**。

---

### 原则 1：复用优先，相同的东西绝不做第二遍

**解决什么问题**：约束 2（Token 昂贵）+ 约束 1（用户不懂代码，一致性要求高）

**原则内容**：
- 组件复用：全系统只有一个表格组件、一个骨架组件、一个浮动面板组件、一套按钮/输入框样式
- 范式复用：所有列表页统一结构，所有编辑弹窗统一区块结构
- 逻辑复用：算金额、校验、搜索、保存逻辑，抽成公共 hooks/工具函数
- 文档复用：通用规则只在架构文档写一次，功能文档只描述本功能差异

**判断标准**：
- 加一个新页面，80% 是复制现有页面结构，只改列定义和接口
- 改一个通用组件，全系统所有地方统一生效
- 新功能里找不到完全独立实现的表格 / 弹窗 / 按钮

**破例条件**：
- 只有当某个交互在全系统只出现一次且未来不可能复用（如特殊的扫码入口）
- 即使破例，先问："能不能给现有组件加个参数实现？"

**反面教材**：
- "这个页面的表格有点特殊，我自己写一个简单版"——结果简单版越写越复杂，两个表格功能重复、样式不一致、改 bug 要改两处
- "这个按钮样式稍微不一样，我写个 inline style"——最后全系统按钮有 10 种大小、8 种颜色

---

### 原则 2：分层隔离，改一个地方不能炸一片

**解决什么问题**：约束 1（用户不懂代码，改坏了修不起）+ 约束 5（历史数据不能错）

**原则内容**：
- 三层架构：显示层只管画、交互层只管键盘/输入/焦点、业务层只管存算——三层之间只通过明确的接口通信
- 骨架和内容分离：AppShell/ViewFrame 骨架永远不卸载，切换页面只换内容区
- 基础数据和业务数据分离：业务数据带快照，不依赖基础数据的当前状态
- 组件 props 接口稳定：内部怎么改都行，传进去的 props 参数不变，外面就不用跟着改

**判断标准**：
- 改表格的虚拟滚动逻辑，不动业务代码
- 调整骨架的 padding，所有页面自动对齐
- 产品改名字，上个月的单子上还是旧名字
- 加一个新功能，只在路由表里加一行，不改现有文件

**破例条件**：
- 只有当两层确实有强绑定的理由（如产品配置子表 brand/unit 跟 product 生命周期完全绑定，必须 CASCADE）
- 破例必须在文档里写清楚理由

**反面教材**：
- 业务组件直接操作表格内部 state——改了表格实现，业务全崩
- 历史单据 include 关联产品表——产品删了单子打不开
- 页面里硬编码骨架的行高 padding——下次统一调整骨架，这个页面歪了

---

### 原则 3：根据数据形态选交互，操作尽量不被打断

**解决什么问题**：约束 4（Excel 习惯 + 开单场景）

**核心逻辑：不是所有地方都要行内编辑，用什么交互取决于数据形态。** 三种数据形态对应三种交互范式：

| 数据形态 | 典型场景 | 交互范式 | 为什么 |
|---------|---------|---------|--------|
| **单字段高频录入** | 采购报价/配货单的明细行录入 | 行内直接编辑 + 浮动面板辅助 | 客户边说边敲，手不离键盘，一秒钟都不能等 |
| **同主体多维交叉矩阵** | 产品编辑里的品牌×单位×价格矩阵 | 弹窗并行展示，表格化编辑 | 一个输入框放不下 5 个品牌 × 3 个单位的 15 种价格 |
| **父子实体一对多** | 客户→多个地址、单据→明细→配货/成本/退款 | 侧边抽屉递进打开 | 看明细不应离开主列表，抽屉一层层开，不挡主上下文 |

**通用原则（适用于所有交互）**：
- **输入自由**：想敲什么敲什么，不强制先选产品才能输数量，不强制先选客户才能开单
- **辅助后置**：输入时给匹配建议（产品联想、客户联想），但不强制选，不选也能存
- **即时反馈**：改数量金额立刻变，没有 loading 等待
- **无保存按钮**：失焦/回车/关闭自动保存，不用手动点保存
- **弹窗不叠罗汉**：禁止三层以上弹窗堆叠；浮动面板是输入辅助，不是模态框
- **危险操作确认**：物理删除、作废单据等低频高后果操作，需要简单的二次确认
- **自动写行为必须可感知（v2.2，用户反馈）**：系统的灵活本意是不限制用户——重名直接复用档案、输入新单位自动建档，都是"录入即生效"。但**任何系统替你自动产生的写行为（复用/建档/补全），都必须让用户感知到**：复用 → 消息提示「已使用现有档案」；自动建档 → 弹确认让用户知晓并同意。用户感知不到底层灵活逻辑，就会随手乱输，在不知不觉中累积几十条垃圾档案（如乱输单位给产品建了一堆没用的单位）。**灵活 ≠ 静默，灵活 = 用户随时知道系统替他做了什么。**

**判断标准**：
- 客户报"25 弯头一个、800 瓷砖三片"，店员能跟着敲完，中间不弹任何打断的窗
- 敲错了直接改，改完回车继续下一行
- 编辑价格矩阵时，弹窗一次看完所有品牌单位的价格
- 看配货明细时，抽屉从右边滑出来，看完关掉，主列表在原地

**破例条件**：无。三种范式覆盖了所有数据形态，如果出现新形态，扩展范式而非硬套。

**反面教材**：
- "请先选择客户才能添加产品"——客户还在报货，先记下来再说
- "产品不存在，请先创建产品档案"——先输文字，回头再补档案
- 单字段高频录入弹个框"编辑数量"——打断思路
- 多维矩阵行内一点一点弹——15 个价格要点 15 次
- 父子明细弹窗套弹窗——开了三层找不到北
- 弹窗里还要手动点"保存"——关了就应该自动存

---

### 原则 4：一套代码双端一致，所见即所得

**解决什么问题**：约束 1（维护两套太复杂）+ 约束 2（Token 成本）+ 约束 4（不用重新学）

**原则内容**：
- 所有设备渲染完全相同的 DOM 结构，不做响应式重排，不做两套组件
- PC 屏幕大就居中展示，手机屏幕小就局部滚动——保持同样的布局密度
- 修一个样式 bug，PC 和手机同时修好

**实现方式**（由原则推导，不是原则本身）：
- 固定画布宽度（min-width: 1200px），所有尺寸用固定 px
- 禁止 @media 查询改布局，禁止 useIsMobile 切换组件树
- 不 flex-wrap，grid 不用 1fr

**判断标准**：
- 电脑上调好什么样，手机打开一模一样，只是要横向滚动
- 不用写"这个地方手机端改成这样"的代码

**破例条件**：
- 只有键盘弹出这种纯运行时的行为（用 visualViewport 算高度）可以用 JS 处理
- 例外必须是无法用 CSS 表达的，不是"手机上这样更好看"

**反面教材**：
- 手机上把表格改成卡片列表——店员在手机上也要录单，卡片列表效率极低，还要重新学
- 手机上隐藏某些列——信息找不到了
- 搞两套组件 MobileTable 和 DesktopTable——改个 bug 要改两处，Token 花双倍

---

### 原则 5：约定大于配置，目录位置就是配置

**解决什么问题**：约束 1（用户不懂配置）+ 约束 2（Token 成本）

**原则内容**：
- 目录即配置：文件放在哪个目录下，就自动获得对应的导航、权限、骨架
- 扫描即发现：新增一个页面文件，放到 pages 目录下，自动出现在导航里
- 文件名是 ID：文件名叫什么，路由就是什么，导航标题就是什么
- 约定好的骨架、样式、交互，默认就带上——不用每个页面重复声明

**判断标准**：
- 加一个新管理页面：新建一个 tsx 文件，写好列定义和接口，放到对应目录——完事
- 不用改路由、不用改导航配置、不用改权限配置（除了加权限码）

**破例条件**：
- 工作台这种特殊页面有自己的九视图结构，但工作台内部也遵循自己的约定
- 不按约定的页面必须是极少数，且在文档里说明

**反面教材**：
- 每个页面在路由表里写 50 行配置——新加页面要改 3 个地方
- 导航写死在 Layout 组件里——加导航要改骨架代码

---

### 原则 6：文档与代码同步，文档是唯一真理源

**解决什么问题**：约束 1（用户只能靠文档理解系统）+ 约束 2（AI 读文档就能干活）

**原则内容**：
- 先改代码，立即同步文档——同一轮对话内完成
- 每个功能文档自包含：表结构、字段、接口、保存逻辑，全在自己的文档里
- 功能文档和架构文档冲突时，功能文档为准——架构文档只讲通用规则
- 改了什么功能，就更新什么功能的文档——不要"以后再说"

**判断标准**：
- AI 读了功能文档，不用问就能知道表长什么样、接口怎么调、保存逻辑是什么
- 用户打开功能文档，看中文就能明白怎么用、有什么规则
- 代码里的逻辑和文档写的一模一样

**破例条件**：
- 临时调试的一次性脚本，不用写文档
- 探索阶段的原型代码，等确定了再补文档——但原型不能上线

**反面教材**：
- 只改代码不改文档——过两周连自己都忘了为什么这么改
- 文档写得像论文，全是术语，用户看不懂
- 多个文档重复描述同一件事——改了一处忘改另一处，不一致

## 第三部分：决策方法论

### 一、日常决策：当原则冲突时，按优先级权衡

原则不是死的，现实中经常有多个原则冲突的情况。按以下优先级判断：

1. **历史数据不能错**（约束 5）—— 底线，数据错了生意就做不了
2. **录入效率不能卡**（约束 4）—— 开单时客户等着，操作卡壳比什么都难受
3. **影响范围不能扩散**（约束 1）—— 改坏一个地方不能炸一片
4. **Token / 复用成本**（约束 2）—— 能不重复就不重复
5. **性能 / 算力**（约束 3）—— 笔记本扛得住就行，不过度优化
6. **"代码好看""架构优雅"**—— 最不重要。好用、稳定、好维护，比优雅重要 100 倍

### 二、规范演进：什么时候应该推翻旧规范

规范不是永恒的。当出现以下情况时，说明旧规范过时了，应该更新：

1. **它解决的问题不存在了**——比如以后部署到云服务器，"算力往前放"就可以调整
2. **它带来的问题比解决的问题还多**——比如某个统一规范导致新功能开发极其别扭
3. **有更简单的方式解决同样的问题**——技术演进了，原来的复杂方案有了更简单的实现
4. **用户明确提出了新的需求，旧规范确实挡路了**——用户的实际使用永远比理论重要

推翻旧规范必须：
- 先在本文件更新"为什么"部分，说明原来的问题变了
- 全局同步整改，不能只改一个地方留下不一致
- 记录在变更记录里，写清楚为什么改、改了什么

### 三、永久底线：无论如何演进都不能动

- 历史单据是快照，永远不变
- 用户不懂代码这个事实不会变（不要期待用户"学会"代码）
- 自然语言驱动开发这个模式不会变
- Excel 式的操作习惯不会变（用户用了十几年，改不了）

## 第四部分：AI 如何理解小白用户的不精确自然语言

> **这部分是给 AI 看的铁则，必须严格遵守。**

用户不懂代码、不懂技术术语、描述随意、经常用比喻、有时候字面意思跟真实意图有偏差。AI 不能抠字眼，不能用户说什么就机械做什么——必须听懂用户"真正想表达什么"。

### 5 条理解铁则

#### 1. 用户说的"所有""全部""永远"，90% 不是真的全部

- ❌ 错误理解：用户说"所有地方都要点格子直接输入"→ AI 把产品编辑弹窗也改成行内编辑，结果价格矩阵没法用
- ✅ 正确理解：先想"用户是在什么场景下说这句话的？他真正觉得不爽的是什么？"→ 用户是在说开单录入的时候不要搞弹窗那套，不是说档案编辑也要硬搞行内
- **判断方法**：回到本文件的约束和原则，用三种交互范式去匹配场景，不是抠"所有"这个词

#### 2. 用户用比喻、举例子、说"像某某那样"，那就是他要的交互

- 用户说"像 Excel 那样"→ 直接对标：点格子直接输、回车下移、改数立刻变、没保存按钮
- 用户说"像微信聊天那样双击弹菜单"→ 直接参考微信的交互模式，不要自己发明
- 用户说"像手写单据那样"→ 就是流式录入，想到什么写什么，不用按顺序填

#### 3. 用户说"不好用""太麻烦""点得累"，不要问"哪里不好用"，自己去看

- 看当前交互比"理想情况"多点了几次？哪里会打断思路？
- 对比 Excel/微信这些用户天天用的软件，是不是多了不必要的点击？
- 多了一次弹窗、多了一个保存按钮、多了一次"请先选择 xxx"——这就是"麻烦"的来源

#### 4. 用户描述矛盾时，看真实使用场景，不看字面

- 用户一边说"所有地方都要自动保存"，一边说"删东西要提示"——这并不矛盾，高频操作不要打断，危险操作要确认
- 用户一边说"要快"，一边说"不能错"——高频快，低频稳，历史数据绝对不能错
- **判断方法**：用第三部分的权衡优先级判断

#### 5. 用户说"就正常项目那样的方式""网上都有现成的"，意思是：

- 不要搞奇技淫巧，用行业成熟的、大家都习惯的方式
- 不要为了"架构优雅"搞复杂的东西，简单直接能用就好
- 文档体系要清晰、不要拆得太碎，让用户（小白）能找到、能看懂
- 符合"约定大于配置"——新文件放对位置就自动工作

### 问问题的正确方式

不要问技术问题，要用业务语言给选项：

| ❌ 不要这么问 | ✅ 应该这么问 |
|-------------|-------------|
| "你是要用行内编辑还是弹窗编辑？" | "这个功能是开单的时候边聊边敲的（像表格那样直接输），还是像编辑产品资料那样一次改很多信息的（弹个窗慢慢改）？" |
| "要不要做响应式？" | "手机上是保持和电脑一样的布局横向滚动，还是专门改个手机版？（我建议保持一样，省得你学两套）" |
| "这个字段要不要加索引？" | 不问，自己判断——这是技术实现细节，用户不关心 |

## 第五部分：现有规范的"为什么"追溯

把现有规范对应到上面的原则和约束，让你明白每个规范不是拍脑袋定的。

| 现有规范 | 解决什么问题 | 对应原则 / 约束 |
|---------|-------------|----------------|
| 固定画布宽度，不做响应式 | 双端一致，不用维护两套，用户不用重新学 | 原则 4 + 约束 1/2/4 |
| **独立模态画布居中（一处抽象）** | 二次确认弹窗/提示弹窗位置漂移不居中，用户找不到、感受乱；统一相对**画布**居中（画布可滚动/缩放，弹窗 fixed 不随动），一处配置全系统生效；消息通知（toast）保持顶部位置；定位型浮层（实时匹配等）锚定触发元素原位，位置/大小均为画布特性，不随屏幕变化 | 原则 1 + 约束 1/2 |
| **画布缩放开放（CSS zoom 查看层）** | 布局仍是固定画布（不重排），但允许用户放大/缩小查看——小屏看不清、给别人展示信息时放大；zoom 是布局级缩放（非 transform），FloatPanel/表格滚动定位自动正确，弹窗/消息在 body 层不随缩放 | 原则 4 + 约束 1/4 |
| 全系统只有一个 UnifiedTable | Token 贵，调一次全局用，样式交互一致 | 原则 1 + 约束 1/2 |
| AppShell / ViewFrame 统一骨架 | 加页面快，改布局统一改，所有页面对齐 | 原则 1/2/5 + 约束 1/2 |
| **三种交互范式（行内/弹窗/抽屉）** | 单字段高频用行内，多维矩阵用弹窗，一对多用抽屉 | 原则 3 + 约束 4 |
| 行内编辑：常驻输入框，无 span↔input 切换 | Excel 习惯，流式录入，开单时一秒都不卡 | 原则 3（单字段场景）+ 约束 4 |
| 失焦自动保存，无保存按钮（所有交互通用） | Excel 习惯，关了就存，不用记着点 | 原则 3（通用）+ 约束 4 |
| 末尾有空行，敲完自动补新行（行内编辑场景） | Excel 习惯，想敲就敲，不用点"新增行" | 原则 3（单字段场景）+ 约束 4 |
| 浮动面板不是模态框，不强制选择 | 流式录入不被打断，先记下来再说 | 原则 3（单字段场景）+ 约束 4 |
| 多维矩阵编辑用弹窗（如产品价格表） | 一个输入框放不下 15 种价格，弹窗里表格一次看完 | 原则 3（多维矩阵场景）+ 约束 4 |
| 一对多明细用抽屉递进（如配货/成本/退款） | 看明细不离开主列表，不弹窗套弹窗 | 原则 3（父子一对多场景）+ 约束 4 |
| 危险操作二次确认 | 删东西/作废单据这种低频操作，确认一下不坏事 | 原则 3（通用例外）+ 约束 5 |
| 业务数据快照 + ID 解耦 | 历史单据不能变，删档案不影响历史 | 原则 2 + 约束 5 |
| 配置子表强关联 CASCADE | 产品的品牌/单位是产品的一部分，生命周期绑定 | 原则 2 |
| 前端算金额，后端只存 | 笔记本算力有限，改数立刻出结果 | 原则 3 + 约束 3 |
| 宽表检索 + FULLTEXT 召回 + 候选集受控 | 几十万 SKU 不能全表扫，索引驱动才不卡 | 原则 3 + 约束 3/6 |
| 建档去重走宽表组合值 + 相似候选交用户 | 复杂多表 + 扁平录入存在灰度地带，既不静默乱建也不静默乱并 | 约束 2/5 + 原则 3 |
| 自动写行为可感知（复用提示 + 建档确认） | 灵活不设限但必须让用户知道系统替他做了什么，防垃圾档案 | 原则 3 + 约束 4 |
| **推算/非真实数据必须颜色区分（进价红、推算色）** | 系统自动带入的数字（进价兜底/推算售价）可能被用户完全信任直接报给客户 → 报错价生产事故；颜色警示让用户一眼识别"真实录入 vs 推算数据"，人工核对再报价 | 原则 3 + 约束 4/5 |
| 功能文档自包含 | AI 读一个文档就能干活，Token 省 | 原则 6 + 约束 2 |
| 目录即配置，扫描即发现 | 加页面简单，不用改多个配置文件 | 原则 5 + 约束 1/2 |
| 操作列放首列，更多菜单收敛 | 单元格是输入空间，复杂按钮不占地方 | 原则 3 + 约束 4 |
| 按钮/输入框/字号/行高全系统统一 | 复用，一致，改一次全系统变 | 原则 1 + 约束 1/2 |

## 一句话总结

> **所有的规范，本质上都是在"小白用户 + 自然语言开发 + 笔记本部署 + Excel 习惯 + 历史数据不可变 + 数据量级巨大"这六个约束下，权衡出来的最优解。理解约束，理解要解决的问题，比记住规范本身更重要。**
