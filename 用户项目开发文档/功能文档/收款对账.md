## 功能概述

### 业务定位

收款对账是单据体系中的**标注层视图**，负责记录单据的收款明细、核销确认，并自动推进单据主状态。在 8 档单据状态机中，收款对账处于 `quote_confirmed`（报价已确认）之后，核销完成后自动推进到 `payment_settled`（收款已结清）。

### 在业务流程中的位置

```
需求待确认(demand_pending) → 报价已确认(quote_confirmed) → 收款已结清(payment_settled)
                                    ↑                               ↑
                                    └── 收款对账视图工作区间 ────────┘
```

- **工作区间**：单据状态为 `demand_pending` 或 `quote_confirmed` 时，收款对账视图可操作。
- **自动推进**：当全部收款记录均已核销（`reconcile_status = 'reconciled'`）且已核销金额合计 ≥ 单据价税合计（`total_amount`）时，系统自动将单据主状态推进为 `payment_settled`。
- **设计原则**：`payment_records` 是单据的标注表，不修改 `document_lines`。收款记录仅记录金额、类型、方式、日期，不与单据行一一对应。

### 三层收款类型

| 类型 | 枚举值 | 说明 | 标签颜色 |
|------|--------|------|----------|
| 定金 | `deposit` | 确认订单时收取的定金 | 品牌色(brand) |
| 尾款 | `final` | 交付前或交付时收取的尾款 | 警示色(warning) |
| 赊账 | `balance` | 赊账方式，后续补收 | 默认色(default) |

### 对账状态

| 状态 | 枚举值 | 说明 | 标签颜色 |
|------|--------|------|----------|
| 待对账 | `pending` | 收款记录已录入，尚未核销 | 默认色(default) |
| 已核销 | `reconciled` | 已与银行/支付平台对账确认 | 成功色(success) |

## 表结构

### payment_records 收款记录表

`payment_records` 是单据的标注表，通过 `document_id` 外键关联 `documents`，级联删除（CASCADE）。

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| id | BigInt | PK, AUTO_INCREMENT | 主键 |
| document_id | BigInt | NOT NULL, FK → documents.id, CASCADE | 所属单据ID |
| payment_type | enum(payment_type) | NOT NULL | 收款类型：deposit=定金 / final=尾款 / balance=赊账 |
| method | varchar(50) | NOT NULL | 收款方式：现金 / 微信 / 支付宝 / 银行转账 |
| amount | decimal(14,2) | NOT NULL | 收款金额 |
| paid_at | DateTime | NOT NULL | 收款日期时间 |
| invoice_info | JSON | | 发票信息（JSON 对象，可选） |
| reconcile_status | enum(reconcile_status) | NOT NULL, DEFAULT 'pending' | 对账状态：pending=待对账 / reconciled=已核销 |
| created_by | BigInt? | | 创建者ID（v11.0 解耦：移除 @relation 物理外键） |
| creatorName | varchar(50)? | | 创建者名称快照（v11.0 解耦：来自 users.real_name） |
| created_at | DateTime | DEFAULT now() | 创建时间 |
| updated_at | DateTime | | 更新时间 |

**索引**：
- `@@index([document_id])` — 按单据查询收款记录
- `@@index([reconcile_status])` — 按对账状态筛选
- `@@index([paid_at])` — 按收款日期排序

**v11.0 解耦说明**：
- `created_by` 移除与 `users` 的 `@relation` 物理外键约束，保留 BigInt? 字段与索引；
- 新增 `creatorName` 快照字段，员工档案删除时收款记录仍可正常展示创建者姓名。

### 与 documents 的关系

```
documents (1) ──── (N) payment_records
```

- `payment_records.document_id` 外键关联 `documents.id`，`onDelete: Cascade`；
- 删除单据时，其下所有收款记录自动级联删除；
- 收款记录不关联 `document_lines`，是单据级别的标注。

### 枚举定义

```prisma
enum payment_type {
  deposit   // 定金
  final     // 尾款
  balance   // 赊账
}

enum reconcile_status {
  pending     // 待对账
  reconciled  // 已核销
}
```

### 接口详情

#### 1. 查询收款记录列表

`GET /api/staff/documents/:id/payments`

**返回**：`PaymentView[]`，按 `paid_at ASC`、`created_at ASC` 排序。

```json
[
  {
    "id": "1",
    "documentId": "100",
    "paymentType": "deposit",
    "method": "微信",
    "amount": "5000.00",
    "paidAt": "2026-08-01T10:00:00.000Z",
    "invoiceInfo": null,
    "reconcileStatus": "pending",
    "createdBy": "1",
    "createdAt": "2026-08-01T10:00:00.000Z",
    "updatedAt": "2026-08-01T10:00:00.000Z"
  }
]
```

#### 2. 查询收款汇总

`GET /api/staff/documents/:id/payments/summary`

**返回**：`PaymentSummary`

```json
{
  "payableAmount": 10000.00,
  "receivedAmount": 8000.00,
  "reconciledAmount": 5000.00,
  "unreconciledAmount": 3000.00,
  "outstandingAmount": 2000.00,
  "byType": {
    "deposit": 3000.00,
    "final": 4000.00,
    "balance": 1000.00
  }
}
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| payableAmount | 应收总额：优先取 `documents.total_amount`，若为 0 则从 `document_lines.amount` 汇总 |
| receivedAmount | 已收总额：所有收款记录金额合计 |
| reconciledAmount | 已核销金额：`reconcile_status = 'reconciled'` 的收款金额合计 |
| unreconciledAmount | 待核销金额：`receivedAmount - reconciledAmount` |
| outstandingAmount | 未收金额：`payableAmount - receivedAmount` |
| byType.deposit | 定金合计 |
| byType.final | 尾款合计 |
| byType.balance | 赊账合计 |

#### 3. 新增收款记录

`POST /api/staff/documents/:id/payments`

**请求体**（`paymentCreateSchema` 校验）：

```json
{
  "paymentType": "deposit",
  "method": "微信",
  "amount": 5000.00,
  "paidAt": "2026-08-01T10:00:00.000Z",
  "invoiceInfo": {}
}
```

| 字段 | 必填 | 校验规则 |
|------|------|----------|
| paymentType | 是 | `deposit` / `final` / `balance` |
| method | 是 | 字符串，1-50 字符 |
| amount | 是 | 正数 |
| paidAt | 否 | ISO 8601 datetime 字符串，默认当前时间 |
| invoiceInfo | 否 | 任意 JSON 对象 |

**返回**：`PaymentView`，HTTP 201。

**后端逻辑**：
- 校验单据存在；
- 创建 `payment_records` 记录，`reconcile_status` 默认为 `pending`；
- 通过 WebSocket 广播 `payment.updated` 事件；
- 记录审计日志（action: `payment_add`）。

#### 4. 更新收款记录

`PATCH /api/staff/payments/:id`

**请求体**（`paymentUpdateSchema` 校验，所有字段可选）：

```json
{
  "method": "银行转账",
  "paidAt": "2026-08-01T14:00:00.000Z",
  "reconcileStatus": "pending"
}
```

**后端逻辑**：
- 校验收款记录存在；
- 仅更新传入的非 `undefined` 字段；
- 通过 WebSocket 广播 `payment.updated` 事件；
- 记录审计日志（action: `payment_update`）。

#### 5. 核销/取消核销

`POST /api/staff/payments/:id/reconcile`

**请求体**：

```json
{
  "status": "reconciled"
}
```

`status` 取值：`pending`（待对账）或 `reconciled`（已核销）。

**后端逻辑**（事务包裹）：
1. 校验收款记录存在，且当前状态与目标状态不同（相同则报 42206）；
2. 在事务内：
   - 更新 `payment_records.reconcile_status` 为目标状态；
   - 若目标状态为 `reconciled`，调用 `maybeAdvancePaymentSettled` 尝试自动推进单据状态；
3. 事务提交后：
   - 广播 `payment.updated` 事件；
   - 若单据状态推进成功，广播 `document.status_changed` 事件；
4. 记录审计日志（action: `payment_reconcile`）。

**自动推进条件**（`maybeAdvancePaymentSettled`）：
- 单据当前状态为 `demand_pending` 或 `quote_confirmed`；
- 所有已核销收款金额合计 > 0；
- 若单据 `total_amount > 0`，已核销金额 ≥ `total_amount`（允许 0.01 精度误差）；
- 满足条件后调用 `transitionStatus(documentId, 'payment_settled', ...)` 推进单据状态。

#### 6. 删除收款记录

`DELETE /api/staff/payments/:id`

**后端逻辑**：
- 校验收款记录存在；
- 物理删除；
- 通过 WebSocket 广播 `payment.updated` 事件；
- 记录审计日志（action: `payment_remove`）。

#### 7. 锁定/解锁视图

`POST /api/staff/documents/:id/payments/lock`
`POST /api/staff/documents/:id/payments/unlock`

**后端逻辑**：
- 在 `documents.view_locks` JSON 字段中设置/清除 `payment_reconcile` 键；
- `view_locks` 的 `payment_reconcile = true` 表示视图已锁定；
- 锁定后前端禁止编辑收款方式、收款日期、核销操作、删除操作；
- 锁定不影响收款记录的查看和汇总统计。

## 保存逻辑

### 前端校验

- 收款金额必须为正数（`Number.isFinite(amt) && amt > 0`）；
- 收款类型必须为 `deposit` / `final` / `balance` 之一；
- 收款方式必须为 `现金` / `微信` / `支付宝` / `银行转账` 之一；
- 收款日期不能为空，默认当前时间。

### 快录行新增流程

```
用户输入收款类型 → 输入金额 → 选择收款方式 → 选择收款日期 → 点击「添加」或按回车
    ↓
前端校验金额为正数
    ↓
调用 addPayment 接口
    ↓
后端创建 payment_records 记录（reconcile_status = 'pending'）
    ↓
WebSocket 广播 payment.updated
    ↓
前端追加新记录到列表 → 重置快录行金额 → 刷新汇总
```

### 行内编辑流程

```
用户修改收款方式（DsSelect）或收款日期（DatePicker）
    ↓
失焦/关闭面板时触发 commitEditLine
    ↓
比对 editBuffer 与原始值，无变化则跳过
    ↓
调用 updatePayment 接口
    ↓
后端更新对应字段 → WebSocket 广播 payment.updated
    ↓
前端更新行数据 → 回写 editBuffer
```

### 核销流程

```
用户点击行尾「更多」菜单 → 选择「核销」或「撤销核销」
    ↓
调用 reconcilePayment(record.id, nextStatus)
    ↓
后端事务内：更新 reconcile_status → 尝试自动推进单据状态
    ↓
WebSocket 广播 payment.updated + document.status_changed（如有）
    ↓
前端更新行数据 → 刷新汇总
```

## 交互细节

### 交互范式归属

收款对账视图遵循以下全局交互范式：

- **Excel超级表格范式**：表格内收款方式、收款日期支持行内编辑（失焦即保存），与 `UnifiedTable` 的行内编辑模式对齐。
- **边用边扩展范式**：快录行输入金额后回车即可新增，无需弹窗，操作不断点。
- **视图防误触锁定范式**：遵循「效率文档§4 视图级防误触锁定」规范，锁定后禁止所有编辑操作，仅保留查看能力。

### 数据刷新机制

- 组件挂载时通过 `useSafeAsyncEffect` 加载全量数据（收款列表 + 汇总 + 单据详情）；
- 通过 WebSocket 监听 `payment.updated` 和 `document.status_changed` 事件，跨视图联动自动刷新；
- 新增/更新/删除/核销操作后自动刷新汇总统计。

### 视图锁定机制

- 锁定状态存储在 `documents.view_locks.payment_reconcile` 字段；
- 锁定：一次点击即锁定（无需确认），提示「已锁定，防止误触」；
- 解锁：弹出二次确认弹窗「解锁后所有收款记录将恢复可编辑状态，确定要解锁吗？」，确认后解锁；
- 锁定后：快录行隐藏，收款方式、收款日期变为只读文本，核销/撤销核销/删除菜单项禁用。

### 编辑缓冲机制

- 行内编辑使用 `editBuffer`（`Record<string, EditBuffer>`）管理各行的编辑状态；
- 修改收款方式/日期时先更新 `editBuffer`，失焦/关闭面板时比对原始值，无变化则跳过提交；
- 提交失败时回滚 `editBuffer` 到原始值；
- 使用 `submittingRef`（`Set<string>`）防止同一行重复提交。

## 与其他功能的关联

### 关联采购报价

- 收款对账视图在单据状态为 `demand_pending`（需求待确认）或 `quote_confirmed`（报价已确认）时可操作；
- 采购报价确认后（`purchase_quote_status = 'confirmed'`），单据进入 `quote_confirmed` 状态，收款对账视图进入可操作区间；
- 收款对账不直接依赖采购报价的数据，但采购报价确认后的价税合计（`total_amount`）是核销金额比对的目标。

### 单据状态流转（8 档状态机 · 全系统唯一权威定义）

> **本小节是全系统 8 档单据状态机的唯一权威定义**。其他功能文档（采购报价 / 配货 / 成本 / 发货 / 售后）涉及单据状态一律**引用本小节**，禁止各自另写片段（架构缺陷台账 P-001 整改落地）。
> **代码真相源**：后端 `DOCUMENT_STATUS_ORDER` / `DOCUMENT_STATUS_LABELS`（唯一实现，与下表一一对应）。

**8 档状态与顺序**（档位即生命周期顺序，档位数值仅用于前后定位与排序）：

| 档位 | 状态键 | 中文名 | 说明 |
|------|--------|--------|------|
| 1 | demand_pending | 需求待确认 | 初始档：客户提交需求 / 员工新建单据 |
| 2 | quote_confirmed | 报价已确认 | 采购报价确认后进入（`purchase_quote_status=confirmed`） |
| 3 | payment_settled | 款项已结清 | 收款全部核销且已核销金额 ≥ 价税合计后进入 |
| 4 | allocation_in_progress | 配货中 | 配货环节 |
| 5 | delivery_completed | 交付已完成 | 交付签收完成后进入 |
| 6 | cost_verified | 成本已核定 | 成本核定完成后进入 |
| 7 | after_sales | 售后处理中 | 售后环节 |
| 8 | archived | 单据最终归档 | 终态：定档归档 |

**流转规则（全局，所有环节共用）**：
- **任意双向可逆**：8 档之间除「相同状态」外任意双向可手动流转，不设单向锁定（代码 `canTransition` 恒返回 true，该函数仅为 UI 提示与未来扩展保留）；
- **自动推进**：各环节标注层完成即自动推进下一档（如收款核销完成 → `payment_settled`）；手动切换不受限；
- **变更副作用**：状态变更触发 WebSocket 广播（`document.status_changed`）+ 审计日志；
- **与报价阶段状态解耦**：客户端价格可见性以 `purchase_quote_status`（报价阶段：pending/confirmed/voided）为准，仅 `confirmed` 时售价对客户可见；与 8 档主状态独立。

**各环节工作区间**（本环节可操作的主状态范围；推进条件细节由各功能文档定义）：
- 收款对账：`demand_pending` / `quote_confirmed` 可操作 → 核销完成自动推进 `payment_settled`；
- 配货 / 交付 / 成本 / 售后：分别在 3~4 / 4~5 / 5~6 / 6~7 档区间，推进条件见各功能文档。

### 关联配货、交付、成本

- 收款对账独立于配货（`allocation_lines`）、交付（`delivery_records`）、成本（`cost_lines`）等标注层；
- 收款记录不关联单据行（`document_lines`），与配货行、成本行无直接关系；
- 收款对账、配货、交付、成本等视图共享同一单据的 WebSocket 刷新通道，任一视图变更可联动刷新其他视图。

### 关联正式区定档

- 销售定档（`archived_orders`）中包含 `paid_amount` 字段，定档时快照当前已收金额；
- 收款记录的创建/修改/删除不影响已定档的销售记录。

### 审计日志

所有收款操作均记录审计日志，`resource_type = 'payment_records'`：

| 操作 | action |
|------|--------|
| 新增收款 | `payment_add` |
| 更新收款 | `payment_update` |
| 核销/取消核销 | `payment_reconcile` |
| 删除收款 | `payment_remove` |
