集合体 × 表 · 特征矩阵

62 张表 × 17 个维度。数据源：backend/prisma/schema.prisma（关系真相源）+ 四个档案页的 slots 配置 + 表功能方法论的形态规则。用来找共性、定位例外、把形态钉成槽位。

点任意行展开「为什么是这样」的特征解释。点表头排序。搜索是全文的——搜 sale_price 会连「单位」一起命中，因为它的解释里写了自己被 sale_price 引用，正好用来反查引用关系。

问题一：为什么产品编辑点「产品名称」触发，供应商管理点「供应商名称」触发？

共性（先说一样的）：名称是集合体根实体的锚点，这是全站统一的入口规则，不是两个巧合。

方法论原文：「一个树形关系图集合体 = 一个管理功能：名称列点开，就能编辑整棵树上所有表」。名称之所以被选中做入口，是因为它在关系图上具备三个唯一性：

  • 唯一标识——product.name 在 (categoryId, name) 上唯一；supplier.name / warehouse.name 同理。点它不会歧义。
  • 树根位置——名称挂在根实体上，树下所有挂载表都能从它到达。
  • 业务指代——人嘴里说的就是这个名字，点名称符合直觉。

差异（再说不一样的）：点了之后去哪儿，由树的深度决定。

产品树 · 深 3 层
product → product_brand → spec → spec_unit → (sale_price / purchase_price / product_image)
供应商树 · 深 1 层
supplier → (supplier_contact / supplier_address)
结论：入口规则相同（点名称），承载方式不同（深树走弹窗、浅树走行内矩阵）。决定因素是「维度数 + 层级深度」这两个特征维度，不是功能口味。

代码侧的证据：供应商 / 客户 / 库房三个档案页共用同一套档案框架，槽位声明完全一致——

SupplierManage: kind: 'name' → 'matrix'(contacts) → 'matrix'(addresses) → 'custom' → 'scalar'
CustomerManage: kind: 'name' → 'scalar'(type) → 'matrix'(contacts) → 'matrix'(invoices) → 'matrix'(addresses) → 'scalar'
WarehouseManage: kind: 'name' → 'matrix'(zones) → 'matrix'(contacts) → 'scalar' → 'scalar' → 'custom'
产品管理是唯一的例外：它没有走这套档案框架的 slots，而是自定义表格 + ProductEditDialog 整树弹窗。这是框架槽位化时最该先收拾的一处——要么把产品也收进槽（深树用「弹窗型槽」），要么明确登记它是合法的深树分支。

问题二：产品矩阵的顺序为什么是 产品信息行 → 品牌行 → 规格行 → 单位行 → 图片行？

答案：顺序 = 关系图的挂载层级深度，从根到叶。每一「行」= 一次挂载 = 图上的一层。

方法论：「挂载树的画法（粒度定层级）：树的每一层 = 一次挂载：粒度到哪一层就挂到哪一层」「多行级联（品牌行→规格行→单位行）整体呈现挂载层级关系，一眼看清」。

代码里的 §A–§E 标注与关系图逐层对齐（ProductEditDialog.tsx）：

§A 产品信息行 分类 | 产品名称 | 备注  ← 深度 0，根实体自己的字段（product）
§B 品牌切换行 CascadeSwitchRow  ← 深度 1，product × brand（product_brand）
§C 规格切换行 CascadeSwitchRow  ← 深度 2，spec 挂在 product+brand 下
§D 单位区 矩阵 + 售价/进价浮层  ← 深度 3，spec_unit 挂 spec 下
§E 产品图片 矩阵  ← 深度 3，product_image 挂 spec 下（与单位同级）

所以决定顺序的是三个因素，按优先级：

  1. 层级深度（主排序）——深的排后面。品牌(1) < 规格(2) < 单位(3)。
  2. 依赖顺序（前置键）——规格必须先选品牌、单位必须先选规格。图上是谁的外键，界面上就排在谁后面。这是一个可以自动推导的硬约束。
  3. 同层内按业务主次——单位和图片都在深度 3，单位在前是因为它是价格/库存的载体，业务权重更高。这一条是唯一需要人工指定的，前两条都能从关系图自动推出。
可槽位化的部分：层级深度和依赖顺序都能从 Prisma 关系自动推导 → 矩阵行序可以自动生成，只留「同层排序」一个人工权重参数。这就是你要找的规律。

另外 §D 里售价/进价没有单独占一行，而是收进单位行的展开面板——因为它们是多键组合（sale_price 是 spec×unit×price_type 三键，purchase_price 是 spec×unit×supplier 三键），方法论规定「跨记录数（一条数 = 多键组合）→ 展开/弹层面板，不占主行格子」。代码用 UnitPriceExpandPanel Popover 实现，与规则一致。

维度交叉验证

选两个维度做交叉统计，格内是表数量。有数字的格子 = 已实现的组合；空格 = 这个组合在项目里不存在——要么是不需要，要么是槽位还没覆盖到（后者就是你要找的缺口）。

从数据里读出来的规律

把落地形态收敛到方法论定义的 7 大槽位后，几条规律自己浮出来了。收敛度 100% 的可以直接钉成槽，分裂的说明还缺一个判定维度。

① 快照层 100% 落多记录矩阵（4/4）。document_lines / inbound_lines / purchase_inbound_lines / reimbursement_bill_lines——单据行无论属于哪个单据集合体，形态完全一致。差异只在「格子里存的是引用还是快照」，形态参数化即可。→ 可直接钉成快照矩阵槽。
② 衍生层 100% 落只读台账（6/6）。product_sku_search、inventory、五张 archived_* 全部只读。方法论「不手填，源保存后同步」在数据上完全兑现。→ 可直接钉成只读槽。
③ 挂载层 9/14 落多记录矩阵，剩下 5 个分裂成两类。切换条 2 个（product_brand / spec，中间层且下挂还有子记录）+ 字典多选 2 个（supplier_business_category / brand，引用已有字典而非创建子记录）。缺的判定维度是「来源类型」——挂载的是子记录还是字典引用，形态不同。
④ 维度数决定行内还是展开。三键 → 展开面板 3/5（sale_price、purchase_price 都在里面）；单键 → 全部行内。与方法论「跨记录数（多键组合）→ 展开/弹层面板，不占主行格子」吻合。键数 ≥ 3 收进面板可以做成硬规则。
⑤ 全局层分裂成信息行(11) + 字典检索+快建(7)。判定条件是有没有父实体：无父 = 集合体根实体 → 信息行（product / supplier / customers / warehouse / documents…）；有父 = 被引用的名单 → 字典（category / brand / unit / price_type…）。这条能从 Prisma 关系直接算出。
⑥ 标注层分裂成多记录矩阵(5) + 只读台账(5)。不是两种形态，是同一个矩阵的两种状态——结清/定档前可编辑，之后冻结。这是「只读/可变」开关，不是新槽位。

槽位化判定链

上面六条合起来，就是一张能自动判定槽位的决策链。每个判断条件都能从 Prisma 关系 + 一条特征配置算出，不需要人拍脑袋。

有父实体吗？
├─ 无 → 信息行槽（集合体根实体，点名称进编辑）
└─ 有 → 在哪一层？
   ├─ 全局层 → 字典检索+快建槽
   ├─ 挂载层 → 挂的是子记录吗？
   │   ├─ 是 → 多记录矩阵槽（默认列开关由「默认语义」定）
   │   └─ 否 → 字典多选槽（引用已有字典）
   ├─ 行级层 → 键数 ≥ 3 吗？
   │   ├─ 是 → 展开/弹层面板槽
   │   └─ 否 → 行内确认层格槽
   ├─ 快照层 → 多记录矩阵槽（快照版）
   ├─ 标注层 → 多记录矩阵槽 + 阶段只读开关
   └─ 衍生层 → 只读台账槽
再叠加三个格级参数（不换槽，只调参数）：来源类型（字典引用 vs 直接值）、依赖顺序（门禁提示）、空行交互（按钮新增 vs 直接追加）。这三个是格级的——同一个矩阵里 method 走字典、value 走直接输入，就是证据。

17 个维度分四组

前三组来自表功能方法论（js/data/gen/01-know-table.js），第四组是「特征分支」——方法论明确规定：这些差异全部在同一组件里用参数注入，禁止为差异另写一个组件。所以第四组其实就是槽位的参数清单。
