### 核心证据（全来自 schema + migrations + src/services）
- **物理外键 vs 逻辑外键混用（🔴）**：11 处注释「无物理外键」，集中在 inventory /
  inventory_ledger / backorders 的 warehouse_id/spec_id/brand_id/unit_id；
  document_lines 有真实 FK（SET NULL）+ 名称快照，是正确范本。
- **名称快照缺口**：document_lines 有 productName/brandName/categoryName/specModel/unitName；
  inventory 家族 0 个 → 删品牌后库存行变孤儿且读不到名（即此前 backorders 缺快照的同一根因）。
- **onDelete**：42 Cascade / 2 SetNull / **0 Restrict**（无 DB 级字典删除护栏）。
- **删除护栏不一致（🔴）**：address_type 有「被 N 条引用即禁删」；brand 只拦 spec 引用
  （brand.ts:162，v14.0）、不拦 inventory；category 只拦 product；warehouse 只拦主仓。
  **系统缺口：没有任何字典删除检查 inventory 引用。**
- **qty 精度分裂**：库存家族 Decimal(14,3) vs 单据/归档 Decimal(12,2)，流转截断+对账漂移。
- **warehouse 是「被遗忘的 sibling」**：name 无 @unique（兄弟都有）、status 用 Int 魔法数
  （兄弟用 enum）、isMain「有且仅一」无约束。
- **主键 ID 类型分裂**：60 BigInt / 3 Int（roles·category·system_config）；同字段 categoryId
  在 product 里 Int、在 supplier_business_category 里 BigInt。历史债，新表建议全 BigInt。
- **软删除缺失**：全库 0 deletedAt，硬删，仅 audit/field_change_logs 记改不记删。
- **枚举纪律是全库唯一强项**：27 枚举广泛生效，仅 warehouse.status 漏。别动。

### 判定与意见
- 合理标杆：document_lines 快照+FK 模式、address_type 护栏、枚举纪律。
- 不合理需修：inventory 家族无 FK+无快照、删除护栏不统一、qty 精度、warehouse 三处。
- 建设性意见（优先级）：P0-11.1 inventory 家族加名称快照 / 11.2 抽共用 assertDictNotReferenced
  拦 inventory+活动单据引用；P1-11.3 qty 统一(14,3)、11.4 warehouse 补约束、11.5 护栏收敛单函数；
  P2-11.6 Int/BigInt 统一、11.7 关键字典软删除/删除审计。
- 验收：typecheck 基线仍 14 错误（本维只加字段/抽函数，不新增）。
