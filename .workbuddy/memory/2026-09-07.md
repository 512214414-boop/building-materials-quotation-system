## 字段级业务默认值「缺省值」键落地（P7 补充，用户拍板方案 A）
- 用户原话「那就改呀，预览不是依据它们自动生成的吗」——拍板方案 A，且点醒：预览页是配置派生的，改配置重跑即变，无需纠结要不要改。
- 问题：真实库 `customers.customer_type String @default("个人业主")` 是**业务默认值**（新客户默认个人业主），类型零值推不出，引擎不能凭空给；但契约 P7 把字段级「缺省」整个退役，导致无键可表达。
- 解决（四处联动）：
  1. 物理层 `客户.客户类型` 加 `缺省值: 个人业主`（并顺手修了该行历史缩进错误：原本 8 空格多 2，YAML 解析报错）。
  2. 结构解释器 gen-db-ddl.mjs 识别 `缺省值` → 生成 `DEFAULT '个人业主'`（文本类加引号，数值/枚举裸值）。
  3. 体检器 gen-layer-map.mjs F_ALLOW 加 `缺省值`（`缺省` 退役键仍红，第 202 行 `fd['缺省']` 精确匹配不误伤）。
  4. 预览页 gen-layer-preview.mjs fieldRowCells 加 dv cell + fieldTableOf/phyRowsOf 两处表加「缺省值」列。
- 关键区分（写进契约铁律2/§2#2b/§7.1/§4 三律4/物理层头注释）：`缺省`(退役)=复读机器零值；`缺省值`(现行)=声明的业务默认值。两档别混。
- 验证：三生成器全过、体检 0 红、`--check` 对拍一致、DDL 出 `DEFAULT '个人业主'`、预览页「缺省值」列渲染（40 处 `>缺省值<`）。
- 教训：YAML 字段缩进必须与同表其他字段对齐，历史遗留的多空格会导致整表解析失败（报错位置在 `客户类型` 字段）。

## 纠错：「缺省值」是伪概念，全量撤回（用户两次纠错 + AI 想清楚）
- 用户第二句话「你检查一下，缺省补充很多还配置得不对，他的作用想清楚」点破两层，AI 之前两轮全走偏：
  1. **客户类型"按名引用"（存字符串非外键 id）本身是历史妥协**——v25 迁了一半：建了 customer_type 字典表、却没把 customers.customer_type 改成外键、也没种子字典，只留 `DEFAULT '个人业主'` 字符串。不该顺着它配缺省。
  2. **缺省的真正作用 = 让"关系上重要、业务上可暂缓"的必填关联字段，录入时先空着、先用起来、以后再补**（只有产品信息时，品牌/分类先落「未分类」「普通品牌」占位）。它是录入体验的降级策略，不是 DB 默认值、也不是"字段没填兜个底"。
- AI 两轮错误（均已撤回）：
  - 第一轮：造字段级 `缺省值` 键，把"个人业主"（客户类型字典的成员）写到引用方客户表字段上，重犯 P7 铁律"兜底成员属于被引用表自己的世界"。
  - 第二轮：给客户类型加 `缺省行`，给"假引用"打补丁。
- **最终结论**：`缺省行` 只适用于**真外键字典**（分类/品牌）；客户类型的问题是"按名引用"历史错误本身，不配任何缺省，进 O3 收敛清单（正确模型=客户.customer_type 改 外键→客户类型.编号 + 客户类型表补兜底成员「个人业主」，动 DB 时统一修）。
- 落地：物理层客户类型表注释 + 差异层「按名引用」说明标注【历史妥协待收敛】+ O3 清单补第③条。
- 教训（铁律级）：**别因为引用方式变了（按名引用 vs 外键）就绕开 `缺省行` 另立字段级键；也别给"该用外键却用了字符串"的历史妥协配缺省——那是给错误设计打补丁，该做的是进 O3 收敛清单。**
- YAML 坑：注释/说明文本里出现 `缺省行: 个人业主` 这种带冒号的短语，会被 js-yaml 当映射键报"bad indentation"（差异层第 18 行踩过）。写配置说明时冒号短语要改写成「补兜底成员"个人业主"」无冒号形式。

## 兜底成员字段级化「缺省值」+ 基础数据强关联归位（用户三连纠错，最终定稿）
- 用户本次点透四件事，AI 前几轮在「缺省值 vs 缺省行 vs 缺省」标签里打转没抓住本质：
  1. **"能推断但理解不到作用"必须落条目**——缺省的作用（不填先占位、将来再补）逻辑能推但 AI 反复才懂，故必须写进契约固定。
  2. **AI 上一轮误删了「缺省值」列，它必须要有**。
  3. **基础数据（字典表）≠ 单据**——客户类型/联系方式类型是强关联字典，就该存外键 id（显示关联名称）；存名称字符串是历史遗留错误、不符范式。快照只属单据类型（订单/入库单，行级锁冻结历史）；基础数据不存快照。
  4. **对照真实代码不能只看"有哪些字段"，要分析字段关系合理性**，不对的按范式重设计。
- **定案**：表级 `缺省行` → 字段级 `缺省值`（配字典唯一名称字段）。语义完整链：外键留空 → 前端按缺省值名称【反查字典→找不到(还没这条记录)→先插入→拿 id 关联】。
  - 4 处缺省值：分类.分类名称→未分类 / 品牌.品牌名称→普通品牌 / 客户类型.类型名→个人业主 / 联系方式类型.方式名称→电话。
- **修正 4 处"按名引用"历史错误为外键**：客户.客户类型、供应商联系人.联系方式、客户联系人.联系方式、库房联系人.联系方式——存字符串→`外键→字典.编号`。快照字段（单据里的 XX名称快照）保留不动（那是冻结历史的正确设计）。
- **差异层撤 2 条「按名引用」**（联系方式类型/客户类型已改外键，不再需要按名引用登记）；D_ALLOW 白名单删「按名引用」。
- **四处联动全改**：物理层 yml（缺省行→字段级缺省值 + 4 外键修正）/ 契约（铁律2、§1.1、§2、§4、§7.1、§8.5 D5、审计器描述、§6 P7追认②）/ 体检器 map（T_ALLOW 去缺省行、F_ALLOW 加缺省值、缺省值校验=去重:是+文本、D_ALLOW 去按名引用）/ 预览 preview（fieldRowCells+fieldTableOf+phyRowsOf+phyGrp 加缺省值列）。
- 验证：体检 0 红、`--check` 对拍一致、DDL 正确生成 customerTypeId/methodId 外键、预览页缺省值列渲染（42 处）。
- **对账 O3 从 7→136**：因 4 字段改外键，配置=正确模型、真实库=历史错误，漂移是预期的 O3 收敛项（DB 反向收敛：改列+回填 id+种子字典）。
- 关键教训（铁律级）：**兜底成员的落点 = 字典表的唯一名称字段（字段级缺省值），不是表头（表级缺省行）；对照真实代码要审"字段关系对不对"，不是只看有哪些字段就照搬——历史库本身就一堆没遵范式的错误，AI 要按范式重设计。**

## 立 P16「改配置工作量铁律」根治返工（用户追问"为什么改这么多文件这么多处"）
- 用户点破核心困惑：加/改一个配置（缺省值），AI 居然动 6 个文件 40+ 处、反复横跳三次——预览不是从源文件生成的吗，为什么这么复杂？
- AI 复盘病根（诚实结论）：
  1. **主因=概念没定稿就急着四处联动、边改边试**：`缺省值` 一个键改了三个方向（字段级→表级→又改回字段级），横跳三次，返工翻倍。若第一次就想透"缺省=不填先占位、反查字典找不到就建行再关联 id"，一遍做完。
  2. **次因=规则散落**：体检器 map 21 处、契约 22 处、预览 6 处「缺省」，其中 3 处是上一轮改漏的「缺省行」旧词残留（正是"散落导致改不全"的铁证）。
- **落地**：① 契约 §0.0 立 P16 铁律（分"改值 vs 新增键"两种；新增键=先契约定稿→一次性改 4 处→--check→完，禁横跳；真相源 3 个 yml 与生成物 .html/.sql 严格分离，人只碰真相源；同一概念契约定义一次、生成器各消费一次，不重复抄文案）；② §6 补 P16 决策登记；③ 版本页脚更新；④ 清掉 3 处「缺省行」旧词残留（map 第459行、preview 第411/510行），三生成器源码旧词归零。
- 验证：体检 0 红、--check 对拍一致、预览页正常。
- 关键教训（用户红线级）：**用户极度反感"一个简单问题动一堆文件一堆处"。改配置必须分两种——改值=只动 yml 一处；新增键=先定稿再一次性落地。禁止边改边试、禁止横跳返工。真相源与生成物严格分离，生成物一个字都不手改。**
