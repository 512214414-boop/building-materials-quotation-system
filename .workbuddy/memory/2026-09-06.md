## 两条高价值教训（本轮真实踩坑，值得沉淀）
1. **归因必须验到底**：架构师与我一度认为 44 处 custom 源于生成器 `?? 'custom'` 兜底。实测 yml 110 条 column **零条缺省 renderMode**，44 处全是**显式写在 yml 里**。→ 「只改生成器即可归零」不成立，必须生成器+yml 双管。**若按错误归因动手，44 处一个都不会消失，却会误以为任务完成。**
2. **静默失败被当成取证（两位工程师独立踩同一个坑）**：macOS 自带 **BSD grep 在 BRE 下不支持 `\|`**，`grep "a\|b"` 会退化成搜字面量 `a|b`，返回**零匹配而非报错**。两人分别据此误判「非生成物 0 处 custom」「文件里没有重复声明」。→ 教训不是"grep 不好用"，而是**零匹配不能直接当结论**；可疑时用 `grep -c` 自校（先验证能匹配到的已知串）或换 `grep -E 'a|b'`。本项目已有「门禁不许静默跳过」纪律，此为其命令层对应物。

## 检索权重两层解耦（用户纠正：物理层权重只管本表、关系层级权重天然）

## P8 检索参数 → 索引级别制（19:5x 用户四连问"凭什么按产品名称搜不是备注"）
- 用户纠错：`检索: {本表权重: 主·次·辅}` 配置方式不对。本质=产品名称被配成【主索引】、备注为【子索引】；规则=①配了(非空)即参与本表检索匹配 ②数字小=命中优先 ③为可扩展应叫 1级索引/2级索引、可同级重复(同级=并列)。"权重"词误导(与排序/层级权重撞车)、文言三档不可表达同级并列。
- 查证：后端 resourceController searchFields 默认 ['name']（无 search.fields 配置时死规则）；entity-meta 用 searchLayer: name 仅声明未消费；search-scoring 是单据精确匹配另一套。→ 检索参与集/优先级真相源空白，正是该由物理层级别填充。
- 定稿（契约 v5 + P8）：字段级 `检索: {级别: N}` 正整数；1级=主索引(关系层每层主字段应指向它，体检黄项)/2级=子补充；落地 yml 10 字段按语义定级(7 个名称类字段=1、3 个备注=2)；map 加级别正整数红项+旧键`本表权重`红项+主字段→1级黄项；preview 标签"N级索引 · 主/子"+全文案重写(参与集不再"偷取全部text"、优先级=级别映射命中分)；gen-entity-meta ⑥ searchTier(主/次/辅文言)→searchLevel:number(生成物 10 处)。四件套 0 红、对拍通过。
- 教训延续：用户每句"凭什么/怎么会"都是揪出「配置写了模糊词而解释器无从定死语义」——检索的参与集与优先级必须字段级可判定，不能靠框架猜/文言。

## P9 检索链抽象定稿：模式切换=层级切换 + 物理层=DB结构唯一画布（20:0x 用户升维追问）
- 用户抽象（正确，收编）：① 模式切换=关系层通路切到哪一层（有几级/每级主实体=关系层配置）；② 切到后搜哪些字段/谁优先=物理层检索级别集（P8 已就位）；③ 打分=引擎唯一一套规则——写死的是规则不是业务（守住宪法：公式不进配置，特例走差异层调级别）；④ 消费端（后端只搜 name 死规则）是断点，属 O4 阶段2。新表只要配好级别即零检索代码。
- DB 索引事实（标准答案）：索引不自动长（主键/唯一约束/外键列除外——库自动补建）；普通索引必须在建表 DDL 一次声明，之后库自动维护、查询自动使用，无"手动开索引"概念。
- 划界（诚实）：`去重:是`=唯一索引（防重+查重快，物理事实）✓；外键列自动带索引 ✓；但 `检索:级别` ≠ 普通索引——中文业务搜索是中间片段匹配(%瓷砖%)，B-tree 对左通配无效（物理限制）。级别管"搜得准"，索引管"查得快"，两件事；行数少扫表即可，真慢再按需补（差异层登记）。
