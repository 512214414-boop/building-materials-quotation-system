# 方法论详解：顶层设计驱动的文档整理

> 配套 `SKILL.md`。本文把用户口述的哲学展开成可操作的判据，供 AI 在梳理 / 检查 / 演进时内化。

## 1. 三个世界的划分

| 维度 | 一类活（行业本源） | 开发约束（哲学/规范） | 细节（现状） |
|------|-------------------|----------------------|-------------|
| 回答的问题 | 门店有哪几类活？线下怎么干？要达成什么？ | 这个项目怎么跟 AI 开发？各块怎么连？ | 现在具体怎么实现？ |
| 来源 | 现场作业，与框架无关 | 用户约束 / 协作方式 | 当前代码、库表、交互 |
| 换项目 | 同行业大部分带走 | 协作方式像才带走 | 不带走 |
| 文档落点 | 文档可视化 · 指导思想 | 项目设计哲学 / 顶层设计规范 / 架构原则 | 功能文档 / 技术架构 |

关键认知：**细节不是错误，但细节没有自己的"归处"才是错误。** 每一份细节都必须能回答「我是从哪一类活的哪条效果推下来的」。禁止用页面反推业务。方法见技能 `work-kind-first`。

## 2. 为什么必须自上而下，而不是自下而上

自下而上的积累路径是：写功能 → 写功能 → 功能间出现重复 → 加补丁规则 → 补丁之间冲突 → 文档膨胀、没人敢动。

自上而下的路径是：

```
门店一类活（现实怎么干 → 要达成的效果）
   ↓
开发约束（哲学为什么 / 规范理念 / 架构原则）
   ↓ 自上而下推导
各功能文档（细节，自包含但锚定一类活）
```

当新需求进来，先做"顶层推演"——有可能发现旧顶层组织方式本身就不是最优，于是改顶层，再让细节重新对齐。这样系统始终保持**单一组织权**，不会分裂。

## 3. 四类病灶的定义与判据

### 膨胀（Expansion）
- 单份文档过长，超出人一次能消化的体量（架构原则硬上限 300 行）。
- 同一主题散落多份文档，没有"一处定义"。
- 表现为：文档越改越长、加小节而非抽公共、历史记录残留（违反"历史由 Git 负责"）。

### 断链（Broken traceability）
- 功能文档不引用任何顶层文档（`详见《项目设计哲学》`/`《顶层设计规范》`/`《架构原则·xx》`）。
- `详见《》` 指向不存在的文档名。
- 顶层理念没有对应的下层承载（悬空理念）。

### 越权（Scope violation）
- 架构级文档（架构原则 / 顶层设计规范 / 哲学）写了实现细节：组件名、函数名、代码片段、CSS、像素值、文件路径、接口签名。
- 判据：规则写"应怎么做"，实现由代码承载。架构文档写"调用 `useXxx()` 组件"即越权。

### 重复（Duplication）
- 同一规则在 ≥2 处完整描述，未收敛到单一信息源。
- 表现为复制粘贴式段落、同一张表结构在多处定义。

## 4. 演进的触发与节奏

- **不是每次都演进顶层**。只有以下三种情况才动顶层：
  1. 该规范解决的问题已不存在；
  2. 它带来的问题大于解决的问题；
  3. 用户明确提出了新需求 / 新用户故事。
- 其余时候只做 ①②（梳理 + 检查 + 局部整改），不动顶层主轴。

## 5. 与既有规范的关系

本方法论不取代《文档编写规范》与《系统架构巡检与演进任务书》，而是它们的**文档维度聚焦版**：
- 《文档编写规范》给出"怎么写单份"；
- 《系统架构巡检与演进任务书》给出"架构治理专员"的七步流程；
- 本技能补上"顶层↔细节 的显式溯源""自动发现四类病灶"，以及下面两章的**代码对齐**与**向上抽象·重组综合**能力。

## 6. 代码对齐：让文档回到现实（Phase ③）

文档和代码会各自漂移。诊断完四类病灶后，必须回到代码确认"现实是什么"，否则重组是空对空。

### 为什么要对齐
- 文档描述的东西代码可能已经改了（过时描述）；
- 代码里抽象出了可复用面板/组件，文档却只字未提它能用在哪（**漏记能力**）——你说"抽象出来的面板理论上能用到哪些地方"正是这一类；
- 文档命名与代码命名不一致，读文档的人去代码里找不到对应物，认知断裂。

### 怎么对齐（产出"代码事实"）
从三个事实源提取，作为重组底座：
1. **前端** `frontend/src`：路由表（`App.tsx`/`menu.config.ts`）、页面、关键复用组件与"面板"抽象（如 `UnifiedTable`/`EntityPanel`/`DictRefField`/`ViewFrame`/`RecordExpandPanel`）、设计令牌（`tokens.css`/`COL_WIDTHS`）、共享能力注册表（`SHARED_BADGES` 之类）。
2. **后端** `backend/src`：业务模块文件夹、API 前缀、状态机/定价/检索引擎。
3. **数据模型** `prisma/schema.prisma`：主实体与状态枚举。

### 对齐产出"脱节清单"，三类
- **过时**：文档说 A，代码已无 A（删除/更新文档）；
- **漏记能力**：代码有复用抽象 X，文档没说"用在哪"（补一段"可复用能力：X，用于 P/Q/R"）；
- **命名不一致**：文档叫 A、代码叫 B（统一为单一真相源命名）。

> 判据：文档说 A、代码是 B 时，**先核实代码**，再决定文档改还是代码改，不盲从任一方。

## 7. 向上抽象与重组综合（Phase ④，本技能终点）

这是你真正要的能力：把散落、膨胀、可能脱节的细节，**向上收拢成清晰整体，并实际改写文档**。

### 7.1 向上抽象的原则
- **先找主轴，再减枝节**：从代码事实 + 顶层理念反推"系统到底由几块组成、每块管什么"，而不是把 11 份功能文档平铺罗列。
- **一图胜千言**：用一张分层全景图（用户/业务域/技术基线）让人 2 分钟建立心智模型。
- **可复用能力单列**：代码里真实存在的复用面板/引擎，单独成节并标注"用在哪些页面"，这就是"向上抽象"的果实。
- **数据流讲一条主线**：选最核心的一条（如一张采购单据从建单→报价→配货→发货→成本→对账→归档）串起来，比堆模块清单好懂。

### 7.2 重组的三种动作
- **动作 A 生成《系统全景》**：新人视角总览。骨架见 `templates.md`「系统全景骨架」。必须基于 Phase ③ 代码事实，禁止凭空。
- **动作 B 文档归并/精简**：多份同主题合成一篇；超长文档抽公共到架构原则；与代码脱节段用事实重写。执行前先给方案、用户确认。
- **动作 C 逐篇重写**：仅当某篇确需自顶向下重写时，先确认其顶层依据，再决定留/删/并。

### 7.3 重组铁序（不可乱）
永远**先动顶层**（哲学为什么 / 规范理念 / 架构原则），再让细节重新对齐。禁止自下而上打补丁——那是膨胀的根源。文档与代码**同一轮**同步落地。

### 7.4 怎么判断"重组好了"
- 新人读《系统全景》2 分钟能说清"系统由哪几块组成、一张单据怎么流"；
- 任何一份细节文档都能回答"我从哪条顶层逻辑推下来"；
- 代码里的复用能力在文档里有明确"用在哪"的归属；
- 同主题不再散落多份，超长文档已瘦身。

## 8. 洞察性推演（Insight Synthesis，最高价值）★本技能区别于"目录归并工具"的关键

用户（非技术）用口语描述需求，AI 落档时常把"确定性/限制性"说法**字面固化成死规则**。单纯归并/瘦身不改变这一点；洞察是进一步的**内容级推演**。

### 8.1 为什么需要洞察
- 用户原话是"手段/特例"，不是"意图/通则"。照抄固化会让文档充满互相打架的死规定。
- 把全文档并置，才能看出某条"永远 X"其实是某通用意图的特例，某"弹窗新建"其实违背已立全局范式。
- **洞察级文档** = 写清"为什么这样、真正应该是什么"，而非堆砌用户口述的确定性描述。

### 8.2 三类固化信号（识别什么值得推演）
1. **字面绝对化**：`canTransition 恒 true` 与"归档只读冻结"自相矛盾——用户要"自由回退"，但归档是法律事实终态，不可字面全局恒 true。
2. **局部照抄违背全局范式**：局部"省略号截断/禁用空行/硬编码 28 单位"与已立"名称列 wrap 完整可见 / Excel 末尾空行 / 单位字典边用边建档"冲突。
3. **补丁当设计**：源码硬编码 `SUPERADMIN_USERNAMES`、供应商"默认联系人无论是否指定都写库"——把安全/补全补丁写成规则，未复用已有的 `is_system` 保护角色 / 缺省值注册表通用机制。

### 8.3 推演四步
1. 并置相关片段（功能文档段 + 架构原则 + 代码事实 + 顶层约束）；
2. 标注固化信号类型；
3. 上推意图 / 套用顶层范式 / 复用通用机制，写出"真正应该是什么"；
4. 给出落地建议（改文档的"设计意图"段 / 改代码的通用机制），写回文档而非只改排版。

### 8.4 好洞察的判据
= **哪里被固化 + 组合证据 + 真正应该是什么 + 落地建议**。缺推演结论、只做归并的，不算洞察。

### 8.5 反例：推演翻车（必须承认并作废，禁止硬落文档）

> 用户实战纠偏过三条看似成立、实际推错的洞察。教训：**识别固化信号前，必须先搞清"这条规则适用于哪个维度"，否则会把合法设计误判成死规则。**

1. **「canTransition 恒 true vs 归档终态冻结」——错**。用户原话：落库即归档（数据实时同步进库就是归档态），但"归档"≠"冻结不可改"；数据没有百分之百正确不需要改的，用户要改就正常改。**真正禁止的是系统后台批量偷偷改写历史单（违反快照/法律事实），不是禁止用户正常修改单据。** 错因：把"禁止后台批量改写"和"用户不能修改"混为一谈。
2. **「客户/档案管理禁用空行、走弹窗 违背 Excel 范式」——错**。关键维度：**末尾空行流式录入只适合"使用数据的地方"（单据/订单视图，批量录一堆行）；档案管理（客户/产品/供应商）不适用**——产品管理数据关系复杂（非单主表一行能完成）、档案量随时间增长（末尾空行=先翻到最后一页才能录，无法统计）。所以**档案管理统一走弹窗才是合理的**，与《哲学·约束4》不矛盾（约束4 的末尾空行指单据视图，非档案）。错因：没区分"单据视图 vs 档案管理"这个根本维度。
3. **「28 单位硬编码 vs 单位字典」——错**。用户规则：**档案类字典一律不允许预写数据，统一用兜底形式**（没填就自动补一个；全局字典如单位字典初始为空，从单位字典选唯一的；有档案时从单位规则表选）。代码里的"固定枚举/兜底默认值"是**合法兜底**，不是该删的硬编码。错因：把"兜底默认值"误读成"违规硬编码"。

**铁律**：推演出的洞察若被用户否定/补充，立即作废，绝不写回文档或改代码；并把翻车原因补回本节 8.5，防止同模式再犯。

## 9. 执行纪律（用户明确要求，与四步同等重要）

本技能长期被误用成"体检仪 + 报告生成器"——只扫出病症、产出一堆演示文档，却不真正改文档。必须扭转：

1. **执行优先于产出文档**：四步跑完，直接对现有文档做实际改造（合并/瘦身/重写/上调顶层/写回洞察结论）。**严禁以新建"报告/提议/洞察记录/代码事实"类文档代替实际重组**——那等于又造一层膨胀。唯一允许新建的综述文档是《系统全景》与《溯源映射》；扫描器报告、`_代码事实`、`文档归并提议`、`文档洞察记录` 等中间产物，跑完即删或并入权威文档，不得长期留存。
2. **洞察必须先确认**：动作 D 的洞察结论在写回权威文档 / 改代码前，**必须先用对话提问向用户确认**（"这条对不对？要调整/补充吗？"）。未经确认，洞察只停留在对话，不得沉淀为文档或落地。用户若补充信息，据此修正后再确认、再落地。
3. **结构性重组直接做**：归并/瘦身/重写等结构动作，技能已定义清楚、用户已认可，直接执行，不重复问"要不要做"。
4. **清理自身噪音**：每轮结束自检是否新建了非必要文档；有则立即清理（移回收站，不物理删）。
