# 顶层设计驱动文档治理（重组机版）

## 这个技能到底是什么（一句话）

它是你文档体系的**重组机**，不只是体检仪。它能：扫脉络 → 查病灶 → **读真实代码对齐现实** → **向上抽象、重新组织文档、产出一篇新人两分钟看懂的系统全景**。诊断和引用梳理只是前半截；后半截"动手重组 + 代码对齐"才是你真正要的。

## 你面对的根本问题（来自你的原话）

开发文档会**无限膨胀**：越写越多、越来越不规范，而且**顶层抽象与具体实现细节之间失去了关系**，文档和代码也常常脱节。

正确的关系必须是这样的：

- **一类活** = 门店现实闭环的作业切法；**指导思想** = 作业 + 对象/过程/角色/看数/工具习惯，必须能指导开发、解释实现。规范源在 `文档可视化/`；方法见技能 `work-kind-first`。
- **顶层抽象** = 这个项目的开发约束与组织逻辑（*怎么跟 AI 开发、各块怎么连*），由用户需求驱动，是落地层的主轴，本身也可变。
- **细节** = 当前代码/功能的描述，是实现**现状**，不是真理、会变、会漂移。
- **组织权在一类活 + 顶层**：细节以它们为中心组织；禁止用页面/表反推业务。
- **演进自上而下**：新需求 → 先问属于哪一类活 → 必要时回哲学重新推演 → 再推导各层。

没有这个关系，代码无限膨胀，细节越写越多，对**理解项目、帮助项目演进**毫无意义。更糟的是——**文档描述会和真实代码脱节**（比如文档说的"面板/能力"在代码里早换了个样子，或代码里抽象出的复用组件文档根本没记录它能用在哪）。

> 本技能把这套哲学变成**四步可执行动作 + 两个扫描器**，完全站在你既有的《文档编写规范》《系统架构巡检与演进任务书》之上，不另立 competing 规范。

## 四步流程（串行，不跳步）

### ① 梳理（建脉络）——先不管好坏，把现状理清

- 运行 `scripts/scan_docs.py --root "<文档根>"`，产出层级分布 + 四类病灶初筛。
- 生成/更新《溯源映射》（格式见 `references/templates.md`）：每张功能文档 ← 哪条顶层设计理念/架构原则；每条理念 ← 哪条用户约束（项目设计哲学）。
- 目标：让"顶层↔细节"关系**显式、可查**，找出孤儿细节。

### ② 检查（对照基线）——用 `references/inspection-checklist.md` 逐项对照

抓四类病灶（扫描器已初筛，这里人工判定是否真问题）：

- **膨胀**：单份过长（架构原则硬上限 300 行，其余 >300 预警、>500 严重），或同主题散落多份。
- **断链**：`详见《》` 指向不存在的文档；功能文档没回溯顶层。
- **越权**：架构级文档写实现细节（组件/函数/代码/CSS/像素/路径/接口签名）。
- **重复**：同一规则多处完整描述，未收敛到单一信息源。

### ③ 代码对齐（回到现实）——读真实代码，给重组做事实底座  ★核心新增

> 这是"向上抽象、重新组织"的前提：不读代码，重组就是空对空。

- 运行 `scripts/extract_architecture.py`（或手动探查 `frontend/src`、`backend/src`、`prisma/schema.prisma`），提取**代码事实**：
  - 前端真实路由/页面、关键复用组件与"面板"抽象（如 `UnifiedTable`/`EntityPanel`/`DictRefField`/`ViewFrame` 等）、设计令牌、共享能力注册表；
  - 后端真实业务模块、API 前缀、状态机引擎；
  - Prisma 真实数据实体。
- 把代码事实与文档比对，产出**脱节清单**：
  - 文档描述了但代码已不存在/已变更的东西（过时描述）；
  - 代码里抽象出、文档却没说"能用在哪里"的复用组件/面板（**漏记的可复用能力**——这正是你说的"抽象出的面板理论上能用到哪些地方"）；
  - 文档与代码命名不一致（如文档叫 A、代码叫 B）。
- 这一步的输出是 Phase ④ 重组的**事实输入**，不是给人看的报告。

### ④ 向上抽象与重组综合（动手重组）——本技能的终点  ★核心新增

这是你最想要的环节。从"散落细节 + 代码事实"里**向上收拢成清晰整体**，并实际改写文档。三个动作可单独也可一起做：

**动作 A — 生成《系统全景》（新人视角，最高优先级交付）**
一篇**短、清、自上而下**的总览，让不懂的人两分钟建立系统心智模型。骨架见 `references/templates.md` 的「系统全景骨架」：分层（用户/业务域/技术基线）→ 一张全景图（系统由哪几块组成、每块管什么）→ 关键抽象（代码里真实存在的复用面板/引擎，标注"用在哪"）→ 核心数据流（一张单据从建到归档怎么流）→ 文档地图（每篇文档一句话职责 + 该看哪篇）。**必须基于 Phase ③ 的代码事实写，不能凭空**。

**动作 B — 文档归并/精简（先顶层后细节）**
基于梳理+对齐的发现，提出并**执行**归并：
- 多份同主题、可合成一篇的 → 合并，旧篇改为"详见《合并篇》"的薄壳或删除；
- 超长功能文档 → 抽公共到架构原则，本篇只留"自包含但精简"的差异部分；
- 与代码脱节的段落 → 用代码事实重写。
- 归并提议格式见 `references/templates.md` 的「文档归并提议」，执行前先给用户看方案、确认再动。

**动作 C — 逐篇重写（仅当需要）**
按"先动顶层再推细节"原则，对指定文档做自顶向下重写：先确认其顶层依据（理念/约束），再据此决定留/删/并，产出更短更清晰的版本。

**动作 D — 洞察性推演（Insight Synthesis，本技能最高价值）★核心新增**
不只是归并/瘦身，而是**对内容本身做推演，产出洞察级结论**。用户用口语描述需求，AI 写进文档时常把"确定性/限制性"说法**字面固化成死规则**；把这些碎片与顶层哲学、代码事实、其他文档并置，往往能洞察出"真正应该是什么"。

做法：
1. **并置相关片段**：把同主题的功能文档段落、架构原则、代码事实、顶层约束摆在一起。
2. **识别固化信号**（三类）：
   - **字面绝对化**：用户说"全部/永远/只能 X"被写成不可变通则，但结合约束实际应是某通用意图的特例（如"canTransition 恒 true" vs 归档终态冻结）；
   - **局部照抄违背全局范式**：用户口述的局部做法（弹窗新建/省略号截断/硬编码列表）与已立的全局交互/数据范式冲突；
   - **补丁当设计**：把安全/补全补丁写成规则，未复用已有通用机制（源码硬编码 admin vs is_system 保护角色）。
3. **推演"真正应该是什么"**：上推到意图 / 套用顶层范式 / 复用通用机制，给出比原文更本质的结论，并标注对文档或代码的建议。
4. **落地**：把洞察结论写回文档（作为"设计意图/为何如此"或"待演进"），而非只改排版——这才是"洞察级文档"。

> 判据：一条好洞察 = 指出"哪里被固化 + 组合证据 + 真正应该是什么 + 落地建议"。没有推演结论、只做目录归并的，不算洞察。

## 洞察推演两阶段流水线（下发执行 AI 模式）

> 当用户的诉求是"推演出底层架构/命名/规范，产出一份可下发的任务书给另一执行 AI 落地"时，走本流水线。它与本技能默认的"洞察→直接写回文档"（动作 D）是**同一套洞察方法的两个输出通道**：动作 D 是 insight 直接落地；本流水线是 insight → **唯一《洞察结果文档》（即任务书）** → 下发执行 AI。后者不违反纪律 #1，因为《洞察结果文档》是**刻意的下发交付物**，不是"用报告代替实际重组"。关键纪律见下方『固定目标文档（始终唯一）』：**全项目只有这一份任务书，任何主题都并入它，禁止另建第二份**。

### 四步（串行，不跳步）

1. **打标签通读**：通读全部输入素材（对话片段 / bug 现象 / 交互描述 / 业务构想 / 零散临时约定），逐段打标签：现象 / 表层诉求 / 深层目标 / 临时补丁 / 显性规约 / 闲聊边角。
2. **横向跨素材比对推演**：① 收表层诉求向上提炼统一深层目标，区分"随口补丁"与"顶层架构意图"；② 找多处反复出现的同类诉求提炼统一底层模型；③ 区分"组件本体要统一改"还是"仅场景配置参数不同"；④ 甄别冲突，选贴合深层目标的全局最优，其余降级临时补丁；⑤ 推演适用边界（理论适用 / 禁用场景）。**所有推断须有多处原文线索，禁止脑补**。
3. **阶段1 猜想校验（初稿，绝不动笔写文档）**：输出固定格式【洞察猜想摘要】——分点写推演得到的架构/逻辑猜想（每条标注素材线索），再把逻辑模糊 / 二选一 / 边界不确定 / 缺支撑的点位提取成确认提问。本阶段**只输出猜想 + 确认问题，严禁输出完整方案、严禁写入目标文档**，等用户校准。
4. **阶段2 定稿输出（用户确认校准后）**：基于校准结论，生成/更新三层结构文档——**顶层抽象层 → 模块规约层 → 落地细节快照层**，附可选附表 / 巡检清单；**增量写入唯一固定目标文档**（已执行项保留、新需求追加为新项，不删除旧项、不复写为空）。

### 五条硬约束（不可违反）

1. 猜想校验阶段绝对不写目标文档；仅用户确认校准完成才允许覆盖写入。
2. 禁止凭空新增用户未提及需求；深层推断须有原文线索；多路线二选一交用户抉择。
3. 定稿后**增量覆盖**固定目标文档：叙事层可刷新，但已执行项（✅）标记原样保留、新需求追加为新项，不删除旧项、不复写为空；始终保留一份最新版且为**唯一文件**。
4. 不生成演示样例文档，只产出可落地正式规约 / 整改文档。
5. 严禁只复制原文做简单归档，必须执行完整深层洞察推演。
6. **禁止第二份任务书**：无论主题多少（交互载体 / 开单 MVP / 信息层 / 浮层全场景 …），洞察结果只写入唯一固定目标文档，绝不为不同主题另建 / 另存第二份任务书文件。
7. **执行层自决（下发模式特有，分层约束）**：任务书只定义"做什么 + 验收标准 + 不变量"，**绝不规定执行顺序、并行/串行、拆解方式**；生成任务书时必须在「执行状态追踪机制」章节内置"执行层自决"纪律——执行 AI 接到任务书即视为完整任务，自行决定如何拆解与执行，一个对话内闭环整改所有待执行项。**分层约束**：① 执行策略类问题（顺序/并行串行/优先级/是否确认计划）严禁问用户，由执行 AI 自决；② 但**业务澄清与真实阻塞类问题**（需求歧义/业务规则不清/字段边界语义待定/缺关键信息/任务描述与代码事实严重冲突需变更范围）**允许且应当主动提问**，属正常交付协作——一句话判据：问"先做哪条"自己定，问"该往哪做对不对"该问就问。

### 固定目标文档（始终唯一）
- **全项目只有一份任务书**：`用户项目开发文档/AI协作/洞察结果文档.md`（即任务书）。任何主题的洞察结果**全部并入这一份文件**，严禁为不同主题新建或另存第二份任务书文件（这是用户明确反复强调的纪律）。
- **增量覆盖（非全量重写）**：每次更新前先读「执行状态总览」→ 已执行项（✅）原样保留标记、不重写 → 用户新需求作为**新增巡检项追加**（不删除、不复写旧项）；架构 / 规约叙述层可刷新重写，但任务清单 + 状态台账始终增量累积。
- 用户指定其他路径则服从，但默认仍遵循"单一文件 + 增量"原则。

**重组铁序**：永远先动顶层（哲学/规范/架构原则），再让细节重新对齐；禁止自下而上补补丁。文档与代码**同一轮**同步。

## 铁律（不可违反，来自你既有规范）

- 历史由 Git 负责：文档正文不写变更记录，直接更新现状。
- 功能文档自包含：表结构/接口/保存逻辑自己定义，不依赖外部补全。
- 唯一裁决链：**用户最新指令 > 项目设计哲学 > 功能文档 > 顶层设计规范 > 架构原则**。
- 规则写文档，实现由代码承载；架构级文档禁止写实现细节。
- 引用代替复制：跨文档用 `详见《文档名·章节》`，禁止复制粘贴式重复。
- 标题即 ID：禁止数字编号标题，标题语义化作锚点。
- **重组以代码事实为准**：文档说 A、代码是 B 时，先核实代码，再决定文档改还是代码改，不盲从任一方。

## 执行纪律（与四步同等重要，用户已明确要求）

1. **执行优先于产出文档**：技能认可后，直接对现有文档做实际改造（合并/瘦身/重写/上调顶层/写回洞察结论），**严禁以新建"报告/提议/洞察记录/代码事实"类文档代替实际重组**——这类演示文档本身是噪音，会制造新一层膨胀。唯一允许新建的"综述类"文档是《系统全景》（用户要的"向上抽象整体"）与《溯源映射》（顶层↔细节归处）；其余中间产物跑完即删或并入权威文档。

**例外（下发模式）**：当用户明确要求"洞察推演 → 下发执行 AI"（走上文『洞察推演两阶段流水线』）时，《洞察结果文档》作为刻意的下发交付物允许新建/覆盖，不视为"用报告代替重组"——它本就是交给另一 AI 落地的任务书，本技能在此模式下不直接重组。
2. **洞察必须先确认**：Phase ④ 动作 D 的洞察结论，在写回任何权威文档 / 改任何代码前，**必须先用对话提问向用户确认**（"这条洞察对不对？要调整吗？"），用户可补充或否定。未经确认，洞察只停留在对话里，不得沉淀为文档或落地；确认无误后才执行"写回文档/改代码"。
3. **结构性重组直接做**：归并/瘦身/重写等结构动作，技能已定义清楚、用户已认可，直接执行，不重复征询"要不要做"。
4. **清理自身噪音**：每轮执行结束自检是否新建了非必要文档；有则立即清理（移入回收站，不物理删）。

## 用法（给用户看）

- "整理一下文档 / 文档又膨胀了" → 跑 ①②③，据报告整改。
- "生成系统全景 / 新人看不懂系统" → 直接走 ③④ 动作 A，产出《系统全景》。
- "这些文档能不能合成一篇 / 太长太散" → 走 ④ 动作 B，先给归并方案再执行。
- "文档跟代码对不上" → 走 ③ 代码对齐，出脱节清单。
- "新加了个 XX 功能" → 先动顶层（④ 动作 C 的"先动顶层"），再推导细节。
- "推演一下这个命名/架构、出份洞察结果文档给执行 AI" → 走『洞察推演两阶段流水线（下发模式）』：阶段1 出猜想摘要等你校准，阶段2 **增量更新唯一任务书**（保留已执行、追加新项，不另起第二份文件）。
- 模板读 `references/templates.md`；检查项读 `references/inspection-checklist.md`；哲学深究读 `references/methodology.md`。

## 两个扫描脚本

```bash
# 文档体检：层级 + 四类病灶
python3 scripts/scan_docs.py --root "<文档根>"

# 代码事实提取：真实路由/面板/模块/实体（给 Phase ③ 用）
python3 scripts/extract_architecture.py --frontend "<frontend/src>" --backend "<backend/src>" --schema "<prisma/schema.prisma>"
```

- 默认文档根 `./用户项目开发文档`；脚本均纯标准库、无依赖。
- 报告写 `<root>/_治理报告_YYYYMMDD.md`；《系统全景》写到 `<root>/系统全景.md`。
