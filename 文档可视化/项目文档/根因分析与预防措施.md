# 根因分析与预防措施（范式化 / 自造结构弯路 · 定稿版）

> 状态：**定稿 2026-09-05**。本文档是"为什么自造宽表/字典、如何主动预防这一类"的分析定稿，
> 与《架构蓝图 v3》（升版中）互为表里：本文档回答"为什么会发生"，蓝图的上半部「自上而下推导链」
> 把预防变成**开工前的必查步骤**。
>
> 一句话结论：**规则蓝图里一直都有（L5=3NF、§3.3 派生须显式 `@escape`），缺的是两样东西——
> 「自上而下的推导链」（业务目标 → 范式判据 → 层落点）和"设计期闸门 + 机器守卫"。**

---

## 0. 双向不对称：先搞清楚"层不清晰"到底指什么

用户最初的困惑是"数据层表关系 / 管理层 / 表格 UI 层 / 平台资产层……层面关系组织不清晰"。
复核后的精确认识是——**层数没错、依赖没错，缺的是两个方向的不对称**：

| 方向 | 回答什么问题 | 现状 | 靠什么保证 |
|---|---|---|---|
| **自下而上（实现期·层落地）** | 东西造好后放哪、依赖朝哪、怎么声明 | ✅ 清晰 | 机制强制：真相源 `entity-meta.yml` → 生成配置 → 平台内核 → UI 装配，单向依赖、有守卫、可验证 |
| **自上而下（设计期·范式选择）** | 业务目标下这数据**天生是什么形状**、该落在哪层 | ❌ 只有软纪律 | 只有一句"先升维再动手"，无硬步骤、无机器守卫 |

> 书架格子很规整，但一本书该归哪个类、要不要拆成两本，书架不管。
> **层清晰 ≠ 范式选对**。用户观察到"数据模型层做好了、一级级单向依赖很清晰"是真的——
> 那是自下而上的收敛；而宽表与自造字典这类弯路，全部发生在自上而下的推导点。

### 案例复盘（product，两个自造结构都已消除）

| 自造结构 | 动机（合理诉求） | 错在哪 | 现状 |
|---|---|---|---|
| 宽表 `product_sku_search` | 搜索性能 | 读缓存没标派生，被 UI/元模型当**结构真相** | ✅ v30（2026-09-02）物理删除，读路径切范式多路召回 |
| 产品名"字典"（旧 flat `name: unique: global` → v23 的 `product_name` 全局字典表） | "产品要唯一" | **"唯一"是约束不是对象**；名字 1:1 归属产品、无第二实体引用，抽字典=过度归一化 | ✅ v23 P1/P2a/P2b 已外科手术式回退（2026-09-05，未落库故无 DB 回滚） |
| product 实体双定义（旧 flat + subject 并存） | 历史残留 | 真相源不唯一 | ✅ 已收口为单定义 |

**落定裁决（2026-09-05 A）**：产品名不需要独立字典，"唯一"用**全局唯一索引**表达——
唯一键从 `[categoryId, name]` 收紧为 `[name]`，一劳永逸消除"跨分类同名歧义"，不建字典、不加关系表。
实证：真实库 290 产品 / 290 不同名 / 跨分类同名 = 0 → 索引可安全建立，无需数据改写。

---

## 1. 这到底是什么问题（定性）

不是"产品管理设计错了"这一个单点，是**一类系统性病**：

> 每一层（L5 数据 / L1 元模型 / L4 表格 UI）各自按"眼前能跑"拼，缺一个统一的
> 「类 → 标准形状 → 层归属」判据；结果**局部可用的优化被提升为结构真理**。
> 而这条缺掉的判据，就是自上而下那一半推导链——它不在任何一层里，它是**跨层的总开关**。

直接表现三连击（均在 product 上出现过）：

| 局部优化（合理诉求） | 被提升为 | 后果 |
|---|---|---|
| 宽表（搜索性能缓存） | 结构真相（UI/元模型依赖其结构） | 前端"聚合回产品"、偏离 3NF 查询 |
| 产品名字典（喂宽表搜索便利 / 实现"唯一"） | 冗余真相（第二份产品名） | 违反真相源唯一 + 3NF 无冗余副本 + **1:1 拆表** |
| 旧 flat `product` 定义 | 与新 subject `product` 并存 | 真相源不唯一（L1 双定义） |

---

## 2. 为什么会这样（根因）

1. **设计期没升维**：原始设计是"让这个页面能跑我的业务"，不是"这是目录类主体的标准 3NF 形状"。
   达标即停，没问"这类数据标准长什么样"。
2. **局部优化晋升结构真理**：宽表（搜索快）、名典（实现唯一）都是合理*诉求*，但没按 §3.3 标注为派生/约束，
   于是成了存储/结构真相。**"唯一"是约束不是对象**——约束用 `@@unique`，只有"词被多对多共享或被第二实体引用"
   （品牌挂多产品多规格、单位被多规格引用、分类被产品和供应商经营范围引用）才值得抽字典。
3. **范式库是"事后沉淀"的，设计动作是"事前发生"的**：v29/v30/v23 都是绕路之后才把范式立正；
   两者之间唯一的接口是检索触发词，而触发词按"听到的页面词"组织（"建产品表"），
   命中不了"名字是属性还是对象 / 该类标准形状"这类范式知识——不知道有它，就不会问出能命中它的那句话。
4. **业务目标陷阱**："能跑 = 完成"，不问"3NF / 标准模式是否已有"。代价滞后到"回过来看"才暴露。
5. **层边界被穿越**：读投影（派生）混进结构真相，UI 反依赖它——违反"禁止跨层打补丁 / 禁止隐式绕过"。

## 3. 为什么"主动"没发生（已有机制为何没触发）

| 蓝图已规定的机制 | product 案例为何没触发 |
|---|---|
| L5 = 第三范式（主表 + 独立字典 + 联结表） | "建表/实体前先核对标准形状"**没成设计期必查步骤**；且**没回答什么时候该抽字典**（缺范式判据） |
| §3.3 派生/逃逸须显式 `@escape: 原因+到期` | 宽表没标 `@escape`，成了隐式绕过（禁止项）但无人判 |
| G1 / yml↔md↔generated 一致性 | 曾只查 JS 重复与生成一致性，没查 yml 内同实体双定义、没查 UI 依赖宽表结构 |
| "禁止跨层打补丁" | 读投影混进结构真相，无人守 |

**结论**：规则在，缺的是把"自觉"变成"必查步骤 + 命令可拦截"。
预防措施 = **在蓝图上补一条自上而下推导链 + 激活既有机制做设计期闸门与机器守卫**，不是新增并行规则。

## 4. 主动预防措施（全部挂靠架构蓝图 v3 的「自上而下推导链」）

### A. 范式判据：开工前先对"该类标准形状"（设计期硬闸门）
任何新建/改实体的第一步不是画表，而是**对象分层与范式判据**，先答四问再落笔：
1. **归类**：subject / row / dictionary / junction（对应"货和人怎么存在"）。
2. **抽字典判据**：这个"词"会被**多对多共享或被第二实体引用**吗？
   - 会 → 抽全局字典（如 brand/unit/category）；改名全局生效、引用按 ID。
   - 不会、纯唯一 → **用唯一索引表达，禁止为唯一造字典**（product.name 案）。
3. **1:1 不拆表**：两张表 1:1 且无第二引用方 = 一张表的两行字段，拆表即过度归一化（product 与 product_name 案）。
4. **派生/读缓存必须 `@escape`**：原因 + 到期条件 + 标注"由范式 regenerate、非结构真相"（宽表案）。

> 落到蓝图 v3：这一节即「自上而下推导链」的正文——业务目标 → 归类 → 范式判据 → 层落点登记（`docs-coverage.md` / `entity-meta.yml`）。推导链回答"造什么形状、放哪层"；L1–L5 纵向栈回答"按声明单向依赖落地"，两半拼成全架构。

### B. L1 真相源唯一守卫（机器守卫，挂靠 G1；✅ 已落地 2026-09-05）
- `entity-meta.yml` 每实体唯一定义；生成器（`gen-entity-meta.mjs` 校验段）拦截 `entities` 段内**同键双定义**（js-yaml 默认静默覆盖，此处显式 exit 1）——直接防住"旧 flat product + subject product 并存"类双定义。
- "为唯一造字典"的 1:1 过度归一化（v23 product_name 案）因元模型未枚举全部跨实体引用、机器无法可靠判定引用 multiplicity，**归入 §4-A 设计期推导链人类闸门**，不进机器守卫（否则会对 brand/unit/price_type 等合法字典误报）。

### C. 层边界 arch-lint（机器守卫，挂靠 arch-lint；✅ 已落地 2026-09-05）
- L4 UI / L1 元数据不得依赖派生宽表的结构；宽表只作读缓存、须有 `@escape` 登记。
- 落地：`check-arch.mjs` 新增 A3 规则——**剥离注释后**扫描 frontend/backend 源码，禁用名清单 `product_sku_search`（已删派生宽表）不得在任何非注释代码中出现（防其作结构真相重新引入）；entity-meta.yml 亦不得再登记该表。注释里的历史说明不算违规，避免误报阻断。

### D. 主动信号前置（方法论动作，已随本流程体现）
- 设计评审时 AI **主动列出"本设计里范式已提供、却自己另搞的结构"**，先消再写码；
- 同类第二次出现 → 自动升级为 L3 候选。

## 6. 验收（怎么知道预防生效）

- 新建/改实体时：先答 §4-A 四问（归类 / 抽字典判据 / 1:1 不拆表 / 派生 `@escape`），答案落档 `docs-coverage.md` 再进编码。
- 设计评审：AI 主动列出"范式已提供却另搞的结构"（D）；出现"想加宽表 / 想为唯一加字典"的冲动时有闸门拦住。
- 机器守卫（B/C 落地后）：同实体双定义 / UI 依赖宽表结构 → 命令红。
- product 现场：产品名跨分类全局唯一（在任一分类新建已存在于他分类的同名产品被拒，提示"产品名全局唯一"）。
